## 〇、模块全景与演进线（面试先讲动机，再讲实现）

```
V1：朴素秒杀（内存判断库存 + 直接扣减）
    查库存 → stock<1 拦截 → update stock-1 → 插订单
         ↓ "判断"和"扣减"两步不原子 → 并发交错 → 超卖（100 张卖出 103 单）
V2：乐观锁版（CAS：扣减时带 stock > 0 条件）★ 库存层面安全了
         ↓ 新需求一人一单 → count 检查 → 并发下两个请求同时查到 count=0 → 一人多单
V3：一人一单（count 检查 + 事务）
         ↓ 检查无锁 → 并发穿透
V4：悲观锁版（synchronized 锁用户 + AopContext 代理进事务）★ 当前版本（单机可用）
         ↓ 集群：两个 JVM 各锁各的 → 锁失效
下一站：分布式锁（04 篇），再往后：Redisson、异步秒杀（Lua + 消息队列）
```

**一句话总结**：秒杀的问题永远是"**多个请求同时读写同一行数据**"。库存用**乐观锁（CAS）**保平安，一人一单用**悲观锁（synchronized 锁用户）**保平安，事务自调用用 **AopContext 代理**救回来——单机到头了，集群就是分布式锁的事。

## 二、全局唯一 ID：RedisIdWorker（原文 ch3.1~3.2）

### 2.1 为什么订单 id 不能用数据库自增

文章给出的两个业务动机 + 技术对比：

1. **信息安全**：自增 id 规律性太明显，竞对拿订单号连续 +1 一猜，就知道你一天卖了多少单——商业机密裸奔。
2. **分库分表**：MySQL 单表容量建议不超过 500W，大了要拆表。拆完逻辑上还是同一张表，各表自增 id 必然重复 → 必须有一个"全局唯一 ID 生成器"。

| 方案 | 有序性 | 占用 | 问题 |
|---|---|---|---|
| 数据库自增 | 全局递增 ✅ | 8 字节 | 分表重复；暴露单量 |
| UUID | 无序 ❌ | 36 字符 | 无序 → 主键是 B+ 树，插入随机位置导致**页分裂**，性能差；太长 |
| **Redis 自增 ✅** | 趋势递增 ✅ | 8 字节 | 需自己拼装结构（本方案） |

> 全局 ID 的理想特性：**唯一性、趋势递增（对索引友好）、不暴露业务信息、生成够快**。

### 2.2 结构：拼一个 64 bit 的 long（白话：三段拼图）

```
1bit 符号位(恒 0) | 31bit 时间戳（相对 2022-01-01 的秒数） | 32bit 序列号（Redis 当天自增）
```

- **时间戳用"相对值"**：`nowSecond - 1640995200(2022-01-01 UTC)`。31 bit 能表示约 69 年 → 撑到 2089 年，够用。省位数的经典套路。
- **序列号**：不是时间，是"这一秒内第几个"，直接拿 Redis `increment` 的返回值——原子自增，天然并发安全，一秒能发 2³² ≈ 42.9 亿个。
- 拼装：`timestamp << 32 | count`——时间戳整体左移 32 位腾出低 32 位空位，`|` 把序列号填进去。

### 2.3 为什么按"天"分 key：`icr:order:yyyy:MM:dd`

1. 32 bit 上限是"每秒 42.9 亿"，但 key 是累计自增的——按天分 key 保证单 key 一天用不完，永不溢出归零撞号；
2. 附赠能力：**按天统计订单量**（`GET icr:order:2026:11:21` 就是今天的单量）。

### 2.4 完整代码（本项目 `utils/RedisIdWorker.java`，Boot3 版）

```java
@Component
public class RedisIdWorker {
    private static final long BEGIN_TIMESTAMP = 1640995200L;  // 2022-01-01 00:00:00 UTC
    private static final int COUNT_BITS = 32;

    private StringRedisTemplate stringRedisTemplate;

    public RedisIdWorker(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    public long nextId(String keyPrefix) {
        //1.生成时间戳
        LocalDateTime now = LocalDateTime.now();
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
        long timestamp = nowSecond - BEGIN_TIMESTAMP;
        //2.生成序列号：按天分 key + 原子自增
        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
        Long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);
        //3.拼接并返回
        return timestamp << COUNT_BITS | count;
    }
}
```

> 🅱️ **与原文差异**：原文构造器注入 + `@Resource` 场景用 `javax.annotation.Resource`，Boot 3 里全部换成 `jakarta.annotation.Resource`（本项目构造器注入写法无需改）。

**温馨小贴士：CountDownLatch（信号枪）——为什么测试类需要它**

300 个线程是异步提交的，主线程如果不管它们，可能分线程还没跑完就往下统计耗时了。CountDownLatch 就是发令枪：`new CountDownLatch(300)` 内部计数器=300，每个线程跑完调 `countDown()` 减 1；主线程 `await()` 阻塞等计数器归 0 再继续——这样测出来的 time 才是 3 万个 id 全部生成完的真实耗时。

```java
@Test
void testIdWorker() throws InterruptedException {
    CountDownLatch latch = new CountDownLatch(300);
    Runnable task = () -> {
        for (int i = 0; i < 100; i++) {
            long id = redisIdWorker.nextId("order");
        }
        latch.countDown();          // 跑完一个线程，枪响一声
    };
    long begin = System.currentTimeMillis();
    for (int i = 0; i < 300; i++) es.submit(task);
    latch.await();                  // 主线程阻塞，等 300 声枪响
    System.out.println("time = " + (System.currentTimeMillis() - begin));
}
```

> **踩坑**：曾自动导入 `javax.swing.text.DateFormatter`（Swing GUI 类混进后端）——IDEA 自动导包遇到同名类要长眼睛，实际用的是 `java.time.format.DateTimeFormatter`。
> **验证结论**：3 万个 id 全部单调递增无重复 → Redis increment 扛住了并发。

## 三、秒杀下单（原文 ch3.3~3.4）

### 3.1 下单要想清楚的两件事

1. **秒杀是否开始/结束**——不在时间段内不能下单（`beginTime.isAfter(now)` / `endTime.isBefore(now)`）
2. **库存是否充足**——不足不能下单（`stock < 1`）

### 3.2 朴素版完整流程（V1，已被淘汰，理解用）

查券 → 判时间 → 判库存 → `update stock-1` → 插订单 → 返回订单 id。

**超卖的时间线推演（白话：两个店员同时看柜台）**：奶茶店只剩 1 杯。店员 A 看了眼柜台（=1，还有！）转身开单；同一瞬间店员 B 也看了眼柜台（=1，还有！）也开单——1 杯的货卖出去 2 杯。

```
线程A: 查库存=1 → 【切走】
线程B: 查库存=1 → 扣减 → 库存=0
线程A: 扣减 → 库存=-1 ❌ 超卖！
```

根因：**"判断"和"扣减"是两步，中间线程随时被切走**。注意不是 update 不安全——单条 `update ... set stock=stock-1` 在 MySQL 层有**行锁**，本身是原子的；漏的是多步逻辑之间的间隙。

## 四、乐观锁解决超卖（原文 ch3.5~3.6）

### 4.1 加锁的两条路

| | 悲观锁 | 乐观锁 ✅（本节用） |
|---|---|---|
| 思路 | 假设必有冲突，先独占再操作（synchronized / select for update） | 假设没冲突，更新那一刻校验条件，不满足就失败 |
| 库存场景 | 把查库存+扣减包进锁 | 在 update 的 where 里带上"库存够"的条件 |

秒杀扣库存是"一行数据的自减"，用乐观锁最合适——不需要锁住整段代码，让数据库行锁兜底。

### 4.2 乐观锁的两种实现

| | 版本号法 | **CAS 法 ✅（本项目）** |
|---|---|---|
| 做法 | 加 `version` 字段，`where version = 查到的值`，更新后 version+1 | 不加字段，`where stock > 0` |
| 缺点/优点 | 每次更新 version 都变，100 个线程几乎 99 个失败——秒杀成功率太低 ❌ | 只要库存>0 就能扣，失败即"库存不足"，语义正确 ✅ |

**为什么秒杀选 CAS**：业务只关心"扣的时候库存还在不在"，不需要精确匹配"我查到的那一版"。

**知识小扩展：ABA 问题**——CAS 的盲区：值从 100→99→100（有人退单回弹），"等于 100"的判断分辨不出中间发生过变化。本项目库存**只减不增**，不存在 ABA；Java 里真有 ABA 顾虑可用 `AtomicStampedReference`（值+版本号一起比）。

**知识小扩展：LongAdder**——CAS 大量线程自旋竞争同一个变量会白耗 CPU，Java 8 的 `LongAdder` 把计数拆到 cell 数组分摊竞争，取值时再求和——高并发计数场景替代 AtomicLong 的选择（我们 ID 生成器用 Redis 自增，天生分布式，是同一思想的另一层实现）。

### 4.3 本项目代码（V2 当前版，`createVoucherOrder` 内）

```java
//6.扣减库存（乐观锁 CAS）
boolean success = seckillVoucherService.update()
        .setSql("stock = stock - 1")                    // set stock = stock - 1（SQL 表达式，不是 Java 相减）
        .eq("voucher_id", voucherId)
        .gt("stock", 0)                                 // ← 乐观锁本体：and stock > 0
        .update();                                      // 影响行数=0 → 返回 false
if (!success) { return Result.fail("库存不足"); }
```

## 五、一人一单（原文 ch3.7）

**需求**：同一张券，一个用户只能下一单（防止引流券被同一人无限薅）。

### 5.1 初步实现（V3）

```java
Long userId = UserHolder.getUser().getId();                     // ThreadLocal 拿当前用户
long count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();
if (count > 0) { return Result.fail("该用户已经购买过一次！"); }
```

**温馨小贴士：一个人也会"并发"吗？** 会。文章列了三种来源：① 用户连点按钮/网络延迟后重复点击；② 浏览器或网关自动重发请求；③ 高延迟下两个请求几乎同时到达。所以哪怕单用户，也可能两条请求同时进到下单逻辑。

### 5.2 V3 的并发穿透（时间线）

```
线程A(用户1): count=0（没买过）→ 【切走】
线程B(用户1): count=0（A的订单还没插进去！）→ 通过 → 下单 ✅
线程A: 通过 → 下单 ✅  ← 同一用户两条订单，穿透成功
```

**为什么不用乐观锁解决这里？** 文章原话的要点：**乐观锁适合"更新"数据（update 带条件天然支持），而一人一单的防护点是"插入"（insert 没有条件可带）**——所以用悲观锁，把"查 + 插"整体锁成临界区。

## 六、悲观锁改造：优化一 → 优化四（原文 ch3.7 演进链）

### 优化一：方法上加 `synchronized`（V3.1，不行）

`public synchronized Result createVoucherOrder(...)` —— 锁的是 this（整个服务对象）：用户 A 抢购时，用户 B、C、D 全部排队。秒杀场景所有流量串行，性能灾难 ❌。

> **温馨小贴士：锁的粒度**——粗粒度锁（锁整个方法/对象/表）简单但并发差；细粒度锁（锁一个用户/一行）性能高但实现讲究。**锁的粒度是并发性能的第一杠杆**：原则是互斥范围刚好覆盖必须互斥的最小集合。

### 优化二：锁缩小到用户（V3.2，接近了）

```java
synchronized (userId.toString().intern()) { ... }
```

- **为什么锁用户**：一人一单只需要"同一用户的请求串行"，不同用户之间本来就该并行——互斥范围缩到最小。
- **为什么 `.intern()`**：synchronized 只在锁**同一个对象**时互斥。`userId.toString()` 每次都 new 新 String——两个请求锁两个不同对象，等于没锁。`intern()` 把字符串放常量池，值相同 → 拿到**同一个池内对象**，锁才真正互斥。
- 小瑕疵：理论上不同用户的字符串 hash 相同时会共享池对象造成误互斥（概率极低），课程先接受，分布式锁章节换更干净的方案。

### 优化三：把锁移到外层，包住整个事务方法（V3.3，还差一步）

优化二的锁在**事务方法内部**：事务还没提交，锁先释放了——锁释放后、提交前的时间窗内另一个请求照样穿透。所以把 synchronized 移到外层 `seckillVoucher`，**锁的范围 ≥ 事务的范围**（先加锁，后进事务）。

### 优化四：AopContext 代理救事务（V4 当前版 ✅）

**问题**：外层调 `this.createVoucherOrder(voucherId)` 是**同类自调用**——Spring 事务靠**代理对象**织入（开事务→执行→提交/回滚都在代理层），this 是原始对象不是代理，`@Transactional` **静默失效**（不报错但没事务，比报错危险）。

**解法**：拿当前 AOP 代理，用代理调：

```java
Long userId = UserHolder.getUser().getId();
synchronized (userId.toString().intern()) {
    //获取代理对象（事务），this 调用会让 @Transactional 失效
    IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
    return proxy.createVoucherOrder(voucherId);
}
```

### 6.x 最终版完整代码（本项目实际代码，Boot3 版）

```java
@Service
public class VoucherOrderServiceImpl extends ServiceImpl<VoucherOrderMapper, VoucherOrder>
        implements IVoucherOrderService {

    @Resource
    private ISeckillVoucherService seckillVoucherService;
    @Resource
    private RedisIdWorker redisIdWorker;

    @Override
    public Result seckillVoucher(Long voucherId) {
        //1.查询优惠券
        SeckillVoucher voucher = seckillVoucherService.getById(voucherId);
        //2.判断秒杀是否开始
        if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
            return Result.fail("秒杀尚未开始！");
        }
        //3.判断秒杀是否结束
        if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
            return Result.fail("秒杀已经结束！");
        }
        //4.判断库存是否充足
        if (voucher.getStock() < 1) {
            return Result.fail("库存不足");
        }
        Long userId = UserHolder.getUser().getId();
        synchronized (userId.toString().intern()) {
            //获取代理对象（事务）
            IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
            return proxy.createVoucherOrder(voucherId);
        }
    }

    @Transactional
    public Result createVoucherOrder(Long voucherId) {
        //5.一人一单
        Long userId = UserHolder.getUser().getId();
        Long count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();  // 🅱️ Long
        if (count > 0) {
            return Result.fail("该用户已经购买过一次！");
        }
        //6.扣减库存（乐观锁）
        boolean success = seckillVoucherService.update()
                .setSql("stock = stock - 1")
                .eq("voucher_id", voucherId).gt("stock", 0)
                .update();
        if (!success) {
            return Result.fail("库存不足");
        }
        //7.创建订单
        VoucherOrder voucherOrder = new VoucherOrder();
        voucherOrder.setId(redisIdWorker.nextId("order"));
        voucherOrder.setUserId(userId);
        voucherOrder.setVoucherId(voucherId);
        save(voucherOrder);
        //8.返回订单id
        return Result.ok(voucherOrder.getId());
    }
}
```

**锁+代理+事务嵌套图（手画题）**：

```
请求 → seckillVoucher（无事务：查券、判时间）
         └─ synchronized 用户锁（最大，先加锁）
              └─ proxy.createVoucherOrder（事务从这里开始/提交）
                   └─ count 检查 → 乐观锁扣库存 → 插订单（同一事务，同生共死）
```

## 七、集群环境下的锁失效（原文 ch3.8，04 篇钩子）

**推演**：部署两台 Tomcat = 两个 JVM。JVM-A 里线程 1/2 用同一份代码，锁对象是同一个常量池字符串，互斥 ✅；JVM-B 里线程 3/4 也互斥 ✅；**但 A 的锁对象和 B 的锁对象是两台机器各自内存里的两个东西**——线程 1 和线程 3 之间毫无互斥。同一用户同时在 A、B 各下一单，一人一单又穿了。

**结论**：synchronized 只能锁住"一个 JVM 内"。要跨机器互斥，锁必须放在所有机器都看得见的地方 → **分布式锁**（大家抢同一把锁，比如 Redis 的 SETNX）。特性要求：可见性（多进程看得到同一把锁）、互斥、高可用、高性能、安全。

## 九、八股结合点

1. **乐观锁 vs 悲观锁**（本项目两个都用了，天然对比素材）：库存扣减=乐观锁 CAS（冲突少、可接受失败）；一人一单=悲观锁（插入场景、必须独占临界区）。
2. **Spring 事务失效八场景**（本项目踩第 1 条）：同类自调用 ✅踩过 / 非 public / try-catch 吞异常 / 受检异常不回滚 / 多线程调用 / 传播行为错 / 未被 Spring 管理 / 存储引擎不支持。
3. **String.intern()**：常量池保证值相同→引用相同，是锁用户能"锁到同一把"的前提。八股延伸：JDK7+ 常量池在堆中；`new String("a")` 创建堆对象+池对象两个。
4. **synchronized 锁对象选择**：this（实例）/ Class（类）/ 业务 key 对象（本项目）——粒度越小吞吐越高。
5. **CAS 与 ABA**：AtomicStampedReference 用版本号解决 ABA；本项目库存只减不增无 ABA；高并发计数用 LongAdder 分摊自旋。

## 十、面试题库

### 🔥 必背五题

1. **秒杀怎么防超卖？** 判断+扣减两步不原子才是根因（update 本身有行锁）。扣减用乐观锁 CAS：`update ... set stock=stock-1 where voucher_id=? and stock>0`，影响行数 0 即失败。不用版本号法：高并发下版本号天天变，成功率极低。
2. **一人一单怎么实现？为什么并发下会失效？** count(user_id, voucher_id)>0 拒绝。失效因为"查"和"插"之间有时间窗，两个请求同时查到 0 就双穿。插入场景乐观锁没有条件可带，所以用悲观锁锁用户。
3. **锁用户怎么实现？为什么 intern()？** `synchronized(userId.toString().intern())`：细粒度、不同用户并行。toString 每次 new 新对象锁不住，intern 保证同 id 拿到常量池同一个对象。锁 this = 所有人串行，性能灾难。
4. **synchronized 里调 @Transactional 方法为什么事务失效？怎么解决？** this 调用绕过 Spring 代理。解法：`AopContext.currentProxy()` + 启动类 `@EnableAspectJAutoProxy(exposeProxy = true)`（我真实踩过缺 exposeProxy 的 IllegalStateException）。追问备选：自注入接口 / 拆到另一个 Bean。
5. **订单 id 为什么不用自增？怎么生成？** 防猜测（商业机密）+ 分库分表防重复。RedisIdWorker：31bit 相对时间戳（2022 起，可用 69 年）+ 32bit 按天 Redis 自增序列号，位运算拼 long；increment 原子保证并发唯一，按天分 key 防溢出+白送日统计。

### ⚡ 追问链

- 超卖 →"乐观锁失败的用户怎么办？"（返回库存不足，秒杀语义下失败合理）→"ABA 在你项目存在吗？"（库存只减不增，不存在；余额类才有）
- 一人一单 →"为什么不加 unique(user_id, voucher_id) 索引？"（可以加，做最后一道兜底；业务前置检查减少无效写库，两者不冲突——加分答法"锁防并发 + 唯一索引兜底"）
- 锁 →"集群下为什么失效？"（锁的是 JVM 内 Monitor，多机各锁各的）→"怎么办？"（分布式锁 SETNX，04 篇）
- ID →"Redis 挂了 ID 怎么办？"（可用性依赖 Redis；可答本地号段/雪花兜底）
- 事务 →"锁和事务谁包谁？"（先锁后事务，锁范围≥事务；反之事务未提交锁先释放，照样穿透）
