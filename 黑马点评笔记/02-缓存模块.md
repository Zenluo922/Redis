## 〇、模块全景与全链路时序

### 0.1 缓存三段式（Cache Aside，本模块所有代码的骨架）

```
请求进来
   │
   ├─ ① 查 Redis ────── 命中 ──→ ② 反序列化直接返回（不碰数据库）
   │
   └─ 未命中
        │
        ├─ ③ 查 MySQL
        ├─ ④ 库里也没有 → 返回错误（正式防穿透方案在本章后文）
        └─ ⑤ 查到了 → 写回 Redis（下次命中）→ 返回
```

**一句话总结**：数据库是数据的唯一权威版本，Redis 只是它的"读放大镜"；读先走缓存，未命中才回源，回源后回写。**牺牲写后的短暂不一致（配合更新策略），换取读性能。**

## 〇A、白话速通：一条线讲懂整个模块（入门先读这节，2026-11-18 补）

> 背景：跟着视频把代码敲完了，但复述诊断发现概念地基是糊的（TTL 是什么都不知道、空串理解反了、逻辑过期完全不会）——这是"手在跑、脑子没跟着跑"的典型状态。本节 = **零术语地基版**，先读这里，后面所有"逐段拆解"就都能看懂了。比喻贯穿全模块，对照表见 〇A.6。

### 〇A.1 整个模块只讲一个故事：把数据库挡在后面

MySQL 扛不住高并发 → 找个挡箭牌。**Redis 就是 DB 前面的小卖部**：店里有货（缓存命中）直接拿走；没货（未命中）才跑工厂（查库），顺手进一批上架（回写缓存），下次就不用跑工厂了。

```
查店（get） → 没货（miss） → 进货（查库） → 上架（回写）
```

这就是**三段式骨架（Cache Aside）**——模块里所有代码（商铺类型、详情、穿透、互斥锁）都是这个骨架，后面每个方案只是往骨架上补一个洞。

### 〇A.2 骨架上的三个洞

| 洞 | 场景（白话） | 补法 | 代码在哪 |
|---|---|---|---|
| 穿透 | 有人专问**根本不存在**的商品，店里永远没货，每次都冲工厂 | 在店里贴张"此货不存在"的告示（存空串 `""`，贴 2 分钟） | 6.3 `queryWithPassThrough` |
| 雪崩 | 全店的货**同一时刻**过期下架，全城人涌向工厂 | 过期日期打散（TTL 加随机）、工厂多开分厂（集群）、门口限流 | 第七节（思路） |
| 击穿 | 店里**最抢手的一款**恰好过期，几百人瞬间同时冲工厂 | 两个补法，见 〇A.3 | 8.2 / 8.3 |

### 〇A.3 击穿的两个补法：本质是一个取舍

- **互斥锁**：进货前先抢钥匙（SETNX），拿到钥匙的**一个人**去工厂，其他人原地歇 50ms 再看货架——工厂只被打扰一次，但所有人都在等。**不脏，但慢。**
- **逻辑过期**：根本不让货下架（物理不设 TTL），只在标签上印"最佳赏味期"（expireTime 存 value 里）。顾客看标签：没过期直接卖；过期了 → 一个店员锁门去仓库补货（异步），**其他人照样拿着旧货结账走人**——没人等，但补货完成前拿到的是旧货。**快，但短暂脏。** 前提：这批货必须**开店前就上架**（预热），否则货架上什么都没有，直接"店铺不存在"。

### 〇A.4 工具类一句话

同一个小卖部流程写三遍太蠢 → 把"进货渠道"当参数传进去（`Function<ID,R> dbFallback` 回调），店（流程）是通用的，货源（怎么查库）每家自带。`this::getById` 就是把"查店铺表"这个动作本身递过去。

### 〇A.5 地基五问（复述诊断实录：当时的答案 vs 正解）

> 2026-11-18 复述检验，五题对了两半——如实记录，复习时先遮住右列自己答一遍。

**Q1：查到空串 `""` 该干什么？**
- ❌ 当时答案："应该在缓存里加一个 null"
- ✅ 正解：**什么都不加**。空串就是告示本身。区分两个角色：**写告示**的是第一个踩坑的人（查库发现不存在 → `set(key,"",2min)` → 返回 null，只有这一次写）；**后面所有人都是看告示**（get 到 `""` → 直接返回 null，不查库）。代码三层判断就是"区分墙上三样东西"：

```
get(key) 拿回来的 json，只有三种可能：
① 真货 '{"id":1,"name":"103茶餐厅"...}' → isNotBlank=true → 返回商品
② 告示 ""（之前有人查过，不存在）       → isNotBlank=false，但 !=null → 返回 null，不查库
③ 什么都没有（从没人查过）              → isNotBlank=false，==null  → 去查库（第一次踩坑的人）
```

【温馨小贴士】`isNotBlank` 为什么必须放第一层：它把 `""` 和 null **都**排除，第二层的 `!= null` 才恰好只拦住告示。两层配合，缺一不可。

**Q2：TTL 是什么？为什么空值 2 分钟、真数据 30 分钟？**
- ❌ 当时答案：不知道 TTL 是什么
- ✅ 正解：**TTL = Time To Live = key 的"保质期"**（秒），到点 Redis 自动删掉这个 key。见过实例：排查登录时 `login:code:xxx ttl=40` 就是在倒数；**TTL=-1 永不过期**（逻辑过期的 `cache:shop:1` 就是它）；**TTL=-2 key 不存在**。空值 2 分钟的两个理由：①恶意请求能把告示贴满全店（内存堆积）；②**告示贴多久 = 真实商品上架后"看不见"多久**（短期不一致的时长）——贴 30 分钟意味着新数据 30 分钟查不到。真数据 30 分钟：商品本来不常变，到期自动撕掉重新进货，数据最终还是和工厂一致。

**Q3：为什么先更新数据库再删缓存？**
- 🟡 当时答案："出错率比较低，具体细节不清楚"
- ✅ 正解：**两个方案都会脏，比的是出事概率**。先删缓存：删完到更新库之间（写库很慢）这个空档，读请求钻进来查旧值回写 → 脏到下次更新，**常态就能撞**。先更库再删缓存：需要"查库+回写"整段比"写库+删缓存"还慢——读比写还慢是反常事件，概率极低。再加兜底：真撞上了，**TTL 到期自动撕掉，脏数据最多活 30 分钟**。（完整时序图见 5.2）

**Q4：互斥锁的钥匙三问**
- 🟡 当时答案："让别的等待一条一条通过"（✅ 对）+"finally 无论如何都会执行"（✅ 但不知道为什么重要）
- ✅ 正解：①**钥匙怎么发**——`setIfAbsent(lockKey,"1",10,SECONDS)`：没人持有我才持有，判断+写入一步完成（原子），100 人同时来只有 1 人返回 true；②**为什么自带 10s TTL**——拿钥匙的人中途挂了（线程崩/宕机），钥匙永远没人还 = 死锁，10s 自动作废保证后来者还有机会；③**为什么 finally 还钥匙**——进货路上抛异常，没有 finally 钥匙要干等 10s 才作废，99 人白等；finally = 无论成败立刻还。附：`if(isLock)` 才还 = **没抢到钥匙的人不能去偷别人的钥匙**。

**Q5：逻辑过期四步**
- ❌ 当时答案：完全不会
- ✅ 正解：①**物理不设 TTL**（Redis 永远不删它，TTL=-1）——凶手是"删除"这个动作，釜底抽薪；②**过期时间写进 value**（`expireTime` 字段 = 赏味期标签，Redis 不认识它，删不删 key 与它无关）；③查询自己判标签：没过期直接返回；过期了 → 抢钥匙，抢到的店员异步补货，**没抢到的和所有顾客拿旧数据立刻走**；④前提：**开店前必须预热上架**——货架上没货它不负责进货，直接 null（"店铺不存在"事故的根源）。

一句话总结：**物理永不过期 + 逻辑自己判断 + 旧数据顶上 + 谁都不用等。**

## 一、商铺类型缓存：课程官方 String 版（骨架版）

课程视频的标准写法，**一个 key 存整包 JSON**：

```java
public Result queryTypeList() {
    // 1. 从 Redis 查询商铺缓存
    String shopTypeJson = stringRedisTemplate.opsForValue().get(CACHE_SHOP_TYPE_KEY);
    // 2. 判断是否存在
    if (StrUtil.isNotBlank(shopTypeJson)) {
        // 3. 存在 → 反序列化直接返回
        return Result.ok(JSONUtil.toList(shopTypeJson, ShopType.class));
    }
    // 4. 不存在 → 查数据库（MP：ORDER BY sort ASC）
    List<ShopType> shopTypes = query().orderByAsc("sort").list();
    // 5. 库里也没有 → 返回错误
    if (CollectionUtil.isEmpty(shopTypes)) {
        return Result.fail("分类不存在");
    }
    // 6. 写回缓存（整包一次序列化）
    stringRedisTemplate.opsForValue().set(CACHE_SHOP_TYPE_KEY, JSONUtil.toJsonStr(shopTypes));
    // 7. 返回
    return Result.ok(shopTypes);
}
```

【拆解】
- **三段式一目了然**：get → miss 查库 → set 回写。第一遍学就写这个版本，把骨架刻进肌肉记忆。
- **`StrUtil.isNotBlank` 而不是 `!= null`**：Redis get 对不存在的 key 返回 null，但判 blank 还顺带覆盖空串 `""`——这是给后文**空值缓存防穿透留的口子**（把空值存成 `""`，下次 blank 判断直接 miss 掉恶意 key，学到穿透那节回头看这行会有第二次收获）。
- **单 key 整包**：写入 `JSONUtil.toJsonStr(整个 List)`，读取一次 `toList`。优点：一次序列化/一次反序列化、一个 key 好管理；缺点：改一条要整包覆盖、无字段粒度。
- key：`cache:shopType:`（`RedisConstants.CACHE_SHOP_TYPE_KEY`），课程此场景**没设 TTL**——数据几乎不变 + 是"预热型"数据；面试被问就说"建议补 TTL + 更新时删缓存"。

## 二、List 版实现逐段讲解（CSDN 参考版，opsForList 练手）

> 来源：CSDN「Purse Wind」黑马点评笔记（原文见参考资料）。**它和官方版的区别**：把整包 JSON 换成 Redis List 的 N 个元素，每个元素是一条 ShopType 的 JSON——顺带把 List 类型的命令全练了一遍。

### 2.1 读缓存

```java
List<String> shopTypeJson = stringRedisTemplate.opsForList().range(key, 0, -1);
if (CollectionUtil.isNotEmpty(shopTypeJson)) { ... }
```

- `opsForList().range(key, 0, -1)` = 命令 **`LRANGE key 0 -1`**：取下标 0 到 -1 的全部元素。**两个下标都是闭区间**，`-1` = 最后一个元素（`-2` = 倒数第二）。
- 返回 `List<String>`：Redis List 每个元素本质是字符串，我们存的是一条条 JSON。
- ⚠️ **key 不存在时返回空 List，不是 null**（LRANGE 对不存在的 key 返回空数组）。所以判空必须用 `CollectionUtil.isNotEmpty()`（对 null 和空集合都返回 false）；写 `!= null` 等于没写。

### 2.2 命中分支

```java
List<ShopType> shopTypes = JSONUtil.toList(shopTypeJson.toString(), ShopType.class);  // ⚠️ 歪写法，见 2.5
Collections.sort(shopTypes, (o1, o2) -> o1.getSort() - o2.getSort());                 // ⚠️ 多余，见 2.4
return Result.ok(shopTypes);
```

### 2.3 未命中分支 + 回写

```java
// 查库，读出时已按 sort 升序
List<ShopType> shopTypes = query().orderByAsc("sort").list();
if (CollectionUtil.isEmpty(shopTypes)) {
    return Result.fail("商铺类型不存在...");
}
// 每个元素单独转 JSON（List 类型的粒度是"元素"，不能整包一起转）
List<String> shopTypesJson = shopTypes.stream()
        .map(shopType -> JSONUtil.toJsonStr(shopType))
        .collect(Collectors.toList());
// 从右边进队保序
stringRedisTemplate.opsForList().rightPushAll(key, shopTypesJson);
return Result.ok(shopTypes);
```

### 2.4 ★ rightPushAll 保序原理（本段精华，想通它就知道 2.2 的 sort 是废话）

```
rightPushAll(key, [A, B, C])        leftPushAll(key, [A, B, C])
  A →  [A]                             A →  [A]
  B →  [A B]                           B →  [B A]
  C →  [A B C] ✅ 与库里顺序一致         C →  [C B A] ❌ 整体反序
```

- 库里 `ORDER BY sort` 有序读出 → **逐个从右边进队**（RPUSH，先进队在左）→ Redis 里从左到右仍升序 → `range(0,-1)` 从左往右取，**天然有序**。
- `leftPushAll` 是逐个从左进（LPUSH），整批进完顺序正好颠倒。
- 所以命中路径上 `range` 拿到的本来就是升序，`Collections.sort` 那行**删掉毫无影响**——能自己发现这点，才算真懂 List 的顺序。**这就是"读有序"和"写有序对齐"：写入顺序 = 读取顺序，中间不需要再排。**

### 2.5 这份代码的 3 个问题（读懂 ≠ 照抄）

| # | 问题 | 为什么是问题 | 改法 |
|---|---|---|---|
| 1 | `shopTypeJson.toString()` 再 toList | `ArrayList.toString()` 输出 `[a, b, c]`，**恰好长得像 JSON 数组**才被解析成功——依赖巧合：可读性差，还要先把整个大 List 拼成一根巨型字符串 | 逐个反序列化，与写入路径对称：`shopTypeJson.stream().map(json -> JSONUtil.toBean(json, ShopType.class)).collect(toList())` |
| 2 | 命中后又 `Collections.sort` | rightPush 已保序（见 2.4），纯多余 | 删 |
| 3 | 没设 TTL | 缓存永不失效，和官方版一样欠妥 | 补 `expire(key, CACHE_SHOP_TYPE_TTL, TimeUnit.MINUTES)` |
| 附 | 减法比较 `o1.getSort()-o2.getSort()` | 极端值溢出（`Integer.MIN_VALUE - 1` 翻正）；本项目 sort 很小无碍，但写法要升级 | `Comparator.comparingInt(ShopType::getSort)` 或 `Integer.compare` |

### 2.6 改进版完整代码（建议照这个写进项目）

```java
String key = CACHE_SHOP_TYPE_KEY;
// 1.查缓存（key 不存在 → 空 List，不是 null）
List<String> typeJsonList = stringRedisTemplate.opsForList().range(key, 0, -1);
// 2.命中：逐个反序列化（List 天然有序，无需再 sort）
if (CollectionUtil.isNotEmpty(typeJsonList)) {
    List<ShopType> list = typeJsonList.stream()
            .map(json -> JSONUtil.toBean(json, ShopType.class))
            .collect(Collectors.toList());
    return Result.ok(list);
}
// 3.未命中查库（读出已按 sort 升序）
List<ShopType> shopTypes = query().orderByAsc("sort").list();
if (CollectionUtil.isEmpty(shopTypes)) {
    return Result.fail("商铺类型不存在");
}
// 4.回写：逐个序列化 → 从右进队保序 → 设 TTL
List<String> jsonList = shopTypes.stream()
        .map(JSONUtil::toJsonStr)
        .collect(Collectors.toList());
stringRedisTemplate.opsForList().rightPushAll(key, jsonList);
stringRedisTemplate.expire(key, CACHE_SHOP_TYPE_TTL, TimeUnit.MINUTES);
// 5.返回
return Result.ok(shopTypes);
```

⚠️ 另一个只有 List 版有的坑：**想用"存空 List"防穿透是不行的**——Redis 空 list 会被自动删除 key，且 RPUSH 空集合直接报错；穿透防护得靠 String 版的空值缓存或布隆过滤器（后文）。

### 2.7 String 版 vs List 版取舍（面试口述）

| 维度 | String 整包（官方） | List 分元素（CSDN） |
|---|---|---|
| 读写开销 | 一次序列化/反序列化 | N 次小转换，但每次粒度小 |
| 修改成本 | 改一条 = 整包覆盖 | 可按元素定位操作 |
| 保序 | 靠序列化顺序 | **结构天然保序**（RPUSH 进队顺序） |
| 空值缓存防穿透 | ✅ 存 `""` 即可 | ❌ 空 list 自动删 key，做不到 |
| 适用场景 | 小且少变的整包数据（本场景就是） | 需要元素级操作/分页的列表 |

**口述版**："商铺类型又小又稳定，String 整包最简单，官方版就够；List 版的价值是练类型、且天然保序，但它没法存空值做穿透防护——数据结构选型要连着后面的缓存问题一起权衡。"

## 三、Lambda & Stream 补课（Java 基础八股结合点）

### 3.1 Lambda 本质：函数式接口的实例

**函数式接口** = 只有一个抽象方法的接口（可加 `@FunctionalInterface` 让编译器检查）。`Comparator` 就是：

```java
@FunctionalInterface
public interface Comparator<T> {
    int compare(T o1, T o2);   // 唯一抽象方法
}
```

Lambda 就是这个接口的实例："参数 -> 方法体"。排序写法的三代演进：

```java
// ① 匿名内部类（史前，5 行）
Collections.sort(list, new Comparator<ShopType>() {
    @Override
    public int compare(ShopType o1, ShopType o2) { return o1.getSort() - o2.getSort(); }
});
// ② Lambda（1 行，参数类型靠推断）
Collections.sort(list, (o1, o2) -> o1.getSort() - o2.getSort());
// ③ 方法引用（地道写法）
list.sort(Comparator.comparingInt(ShopType::getSort));
```

**`compare` 返回值约定（要背）**：负数 → o1 在前；0 → 相等不动；正数 → o2 在前。所以 `o1.getSort() - o2.getSort()` = 升序。减法会溢出，稳写 `Integer.compare(o1, o2)`。

呼应登录模块：`setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString())` 也是 Lambda，类型是 `BiFunction<String, Object, Object>`——同一个知识点。**第十节 CacheClient 的 `Function<ID, R> dbFallback` 参数是这节课知识的总验收。**

### 3.2 Stream 流水线：三段结构 + 等价循环

```java
shopTypes.stream()                                     // ① 源：上流水线
        .map(shopType -> JSONUtil.toJsonStr(shopType)) // ② 中间操作：逐个转换（惰性，只记账）
        .collect(Collectors.toList());                 // ③ 终结操作：真正执行，装车返回
```

看不懂就翻译成普通循环，**语义完全等价**：

```java
List<String> jsonList = new ArrayList<>();
for (ShopType shopType : shopTypes) {
    jsonList.add(JSONUtil.toJsonStr(shopType));
}
```

- 常用中间操作：`map`（一对一转换）、`filter`（元素 -> boolean 过滤）、`sorted`；**惰性**：中间操作只是记流水账，终结操作（collect/forEach）一锤定音才执行。
- 本次用到的 `map()` 的参数类型是 **`Function<T,R>`**（有进有出）。

### 3.3 四大内置函数式接口（认脸版）

| 接口 | 签名 | 一句话 | 用在哪 |
|---|---|---|---|
| `Supplier<T>` | `() -> T` | 无进有出（工厂） | `orElseGet(Supplier)` |
| `Consumer<T>` | `T -> ()` | 有进无出（消费） | `forEach` |
| `Function<T,R>` | `T -> R` | 有进有出（转换） | **stream `map`**、**CacheClient 的 dbFallback** |
| `Predicate<T>` | `T -> boolean` | 判断真假 | stream `filter` |

### 3.4 笔记里那个疑问的答案

"想用 `BeanUtil.copyToList` + `CopyOptions.setFieldValueEditor`" → 不行：`copyToList` 是 **bean → bean** 拷贝，`setFieldValueEditor` 是 `beanToMap`（bean → Map）的编辑器；而本场景要的是 **bean → JSON 字符串**，根本不是一条赛道。stream + `toJsonStr` 就是正确工具，别硬套登录模块的写法。

## 四、商铺详情缓存：Cache Aside 落地（本项目真实代码）

### 4.1 骨架版（先跑通，再谈防护）

key = `cache:shop:{id}`（`CACHE_SHOP_KEY + id`），TTL 30 分钟（`CACHE_SHOP_TTL`）。初版 `queryById`：

```java
@Override
public Result queryById(Long id) {
    String key = CACHE_SHOP_KEY + id;                       // cache:shop:1
    // 1. 从 Redis 查询商铺缓存
    String shopJson = stringRedisTemplate.opsForValue().get(key);
    // 2. 判断是否存在
    if (StrUtil.isNotBlank(shopJson)) {
        // 3. 存在 → 反序列化直接返回
        Shop shop = JSONUtil.toBean(shopJson, Shop.class);
        return Result.ok(shop);
    }
    // 4. 不存在，查数据库
    Shop shop = getById(id);
    // 5. 不存在，返回错误
    if (shop == null) {
        return Result.fail("店铺不存在！");
    }
    // 6. 存在 → 写回缓存（对象 → JSON，设 TTL）
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_SHOP_TTL, TimeUnit.MINUTES);
    // 7. 返回
    return Result.ok(shop);
}
```

【拆解】
- **和商铺类型版唯一的结构差异**：key 是"前缀 + id"——详情是按 id 逐条缓存，类型是单 key 整包。**key 必须拼 id**（踩坑 #3：get 忘拼 id → 永远 miss；这个变量 `key` 在下面 set/delete 还要复用，收敛到一个变量是登录模块的老教训）。
- **`StrUtil.isNotBlank` 的三分支伏笔**：现在它只是"判存在"，等空值缓存上线后，它和 `!= null` 配合变成三分支判断链（见 6.3）——先记住：**blank 判断放最外层，是给 `""` 留的口子**。
- **对象缓存用 String 存 JSON，而登录用户用 Hash——为什么？**（面试高频）详情只做**整体读整体写**，没有字段级修改需求，String 一次 `toJsonStr`/`toBean` 最简单；登录用户有"活跃就续期、可能改字段"的场景且字段少，Hash 支持字段级操作。原则就是登录模块那句：**单值/整体读写用 String，对象且需字段级操作用 Hash**。

### 4.2 方法签名重构（为穿透做准备）

课程在穿透那节把方法重构成"返回 Shop 的私有逻辑 + Result 包装"：

```java
@Override
public Result queryById(Long id) {
    Shop shop = queryWithPassThrough(id);   // 现在你的代码调的是 queryWithMutex
    return Result.ok(shop);                 // shop 为 null 时前端拿不到数据，自然显示查无此店
}
```

为什么重构：让核心逻辑**不依赖 Result 的 HTTP 语义**（返回 null = 查无），后续穿透版/互斥锁版/逻辑过期版都长成一个形状（`Shop queryWithXxx(Long id)`），方便替换对比；也给第十节泛型化铺路。

## 五、缓存更新策略：为什么"先更新数据库，再删除缓存"

### 5.1 三种更新策略（redis 侧视角）

| 策略 | 谁触发 | 一致性 | 成本/维护 | 结论 |
|---|---|---|---|---|
| 内存淘汰 | Redis 自动（内存到 maxmemory 时） | 差（不确定何时发生） | 零维护 | **兜底**，不是方案 |
| 超时剔除 | TTL 到期自动删 | 最终一致（过期前是旧的） | 极简 | **作为兜底保留** |
| 主动更新 | 编码控制（改库时同步操作缓存） | 可控到很高 | 要自己写、要考虑并发 | **主力** |

**课程选型 = 主动更新为主 + 超时剔除兜底**：正常情况靠主动更新保证很快一致，极端漏网情况（更新失败、并发撞车）靠 TTL 到期自动修正——**30 分钟后脏数据必死**，这是一切边角问题的安全网。

### 5.2 主动更新的三个决策点（面试必背）

**决策①：删除缓存还是更新缓存？→ 删除**

| 更新缓存 | 删除缓存 |
|---|---|
| 每次写库都同步写缓存 | 写库后让缓存失效，等下次读时懒加载 |
| 若写多读少：更新 N 次可能一次都没人读 → **N 次无效写** | 只在真正被读时重建，**写操作永远只花一次 DELETE** |
| 还要考虑并发写把缓存写花 | 简单、天然不会写脏 |

这就是**懒加载思想**：不预先付出代价，用到才算。反例场景（写少读多且下次读必然发生）更新缓存才占优，但商户信息"改一条"天然低频。

**决策②：先操作数据库还是先操作缓存？→ 先数据库，再删缓存**

两张并发时序图（白板必画）：

```
方案 A：先删缓存，再更新数据库 ❌（更容易撞车，且脏得更久）

线程1(写)： 删缓存 ──────────────────→ 更新数据库(新值)
线程2(读)：        缓存miss → 查库(旧值) → 写回缓存(旧值) ✘
                                              ↑ 脏值
结果：缓存 = 旧值，一直脏到下次更新/TTL 过期
撞车条件：线程2 的整段"查库+回写"落在"删缓存"和"更新库"之间
         ——写库通常比读库慢得多，这个窗口很容易被读请求钻进来
```

```
方案 B：先更新数据库，再删缓存 ✅（课程选型）

线程1(读)： 缓存miss → 查库(旧值) ─────────────→ 写回缓存(旧值) ✘
线程2(写)：          更新数据库(新值) → 删缓存
结果：也可能脏！但撞车条件苛刻：
     要求线程1"查库"发生在线程2"更新库"之前，
     且线程1"回写"发生在线程2"删缓存"之后
     ——即整个"查库+回写"比"更新库+删缓存"还慢
     （读+写内存 慢过 写库+删内存，几乎不可能，概率极低）
```

两个方案**都不能做到绝对一致**（没有分布式锁就无法根治），选 B 的理由是**发生条件更苛刻 + 发生概率极低**，再叠加 TTL 兜底，实际工程够用。面试就这么说：**"承认理论上有窗口，用概率分析说明为什么选这个顺序，TTL 做最后防线"**——比背死"先库后缓存"高一个段位。

**决策③：怎么保证两步都成功/都失败？→ 事务 + 异常**

- 单体系统：两步放进一个 `@Transactional` 方法（课程 update 就是这么写的）；Redis 操作本身不受 MySQL 事务管理，但**顺序 + try/catch + 抛异常回滚**能保证"库改了缓存没删"时报警出来
- 分布式系统：TCC 等分布式事务，或**删缓存失败就重试**（消息队列）/**订阅 binlog 异步删**（canal）——延伸知识，面试加分项

### 5.3 本项目实现：update（真实代码）

```java
@Override
@Transactional
public Result update(Shop shop) {
    Long id = shop.getId();
    if (id == null) {
        return Result.fail("店铺id不能为空");
    }
    // 1. 更新数据库
    updateById(shop);
    // 2. 删除缓存
    stringRedisTemplate.delete(CACHE_SHOP_KEY + id);
    return Result.ok();
}
```

【拆解】
- **为什么不用 `updateById` 自带的返回值判断**：MP 返回 boolean，课程没判；严格写法应该判 `!updateById(shop)` 失败即 fail。
- **`@Transactional`**：把"改库 + 删缓存"框成一个方法级单元——改库抛异常 → 库回滚，缓存根本没动（删还没执行到）；顺序保证"库没改成，缓存绝不会被删"。注意 Redis 删操作在事务里是**不受回滚保护的**，它排在改库之后，天然只有"库成功"才会执行到。
- **删的是 `CACHE_SHOP_KEY + id`**：和查询用的 key 精确一致（又一个"key 拼装收敛"的应用）。
- **为什么删完不主动回写**：懒加载（决策①），下次查询自动重建。

## 六、缓存穿透：空值缓存（已实现）+ 布隆过滤器

### 6.1 定义

**客户端请求的数据在缓存和数据库中都不存在** → 缓存永远不会被"填上"（查库也是 null，没东西可写）→ 这些请求每次都穿透缓存直击数据库。若被恶意构造（id=-1、超大随机 id 疯狂请求），数据库会被打死。

### 6.2 两大方案对比（讲义原文结构）

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **缓存空对象** ✅ 课程采用 | 查库为 null 时，把空值 `""` 写进 Redis 并给**短 TTL** | 实现简单，维护方便 | ①额外的内存消耗（空值 key 堆积）②**短期不一致**：2 分钟内库上新了数据也查不到 |
| **布隆过滤** | 请求先过布隆过滤器：判断"一定不存在"直接拒绝 | 内存占用小，没有多余 key | 实现复杂；**存在误判**（哈希冲突，说"可能存在"） |

辅助手段（讲义小总结，面试凑数用）：增强 id 复杂度防猜测、入口格式校验、权限校验、热点参数限流。

### 6.3 空值缓存代码逐段（本项目 `queryWithPassThrough`）

```java
public Shop queryWithPassThrough(Long id) {
    String key = CACHE_SHOP_KEY + id;
    // 1. 从 redis 查询商铺缓存
    String shopJson = stringRedisTemplate.opsForValue().get(key);
    // 2. 判断是否存在
    if (StrUtil.isNotBlank(shopJson)) {
        // 3. 存在（真数据），直接返回
        return JSONUtil.toBean(shopJson, Shop.class);
    }
    // 2.5 判断命中的是否是空值
    if (shopJson != null) {
        // 命中 "" → 是之前的空值标记 → 直接返回 null，不查库
        return null;
    }
    // 4. 真未命中，根据 id 查询数据库
    Shop shop = getById(id);
    // 5. 不存在 → 将空值写入 redis（防穿透的核心一行）
    if (shop == null) {
        stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
        return null;
    }
    // 6. 存在，写入 redis
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_SHOP_TTL, TimeUnit.MINUTES);
    // 7. 返回
    return shop;
}
```

**核心读法——三分支判断链（白板必画）**：

```
get(key) 返回 shopJson，三种可能：
┌────────────────────────────────────────────────────────┐
│ ① shopJson 有真数据      → isNotBlank = true  → 返回对象 │
│ ② shopJson == ""（空值）  → isNotBlank = false            │
│                          → shopJson != null → 返回 null   │ ← 穿透防护生效
│ ③ shopJson == null（没key）→ isNotBlank = false            │
│                          → shopJson == null → 查库重建     │
└────────────────────────────────────────────────────────┘
```

- **为什么第一层必须 `isNotBlank` 而不是 `!= null`**：如果写 `!= null`，空串 `""` 会被当成"有数据"拿去 `toBean` → 解析炸/得到脏对象。`isNotBlank` 把 `""` 排除到第二层——**这就是第一节埋的伏笔的兑现**。
- **为什么空值 TTL 要短（`CACHE_NULL_TTL` = 2 分钟，不是 30 分钟）**：①空值是"临时占位标记"不是真数据，30 分钟纯属占内存，恶意 id 请求能把海量空值 key 堆进 Redis；②**短期不一致的时长 = 空值 TTL**——空值缓存 2 分钟意味着"该 id 的真实数据上线后，最多 2 分钟不可见"。**越短越快自愈，但太短防穿透效果打折**，2 分钟是权衡值。
- ⚠️ **你项目里这两行现在写的是 `CACHE_SHOP_TTL`（30 分钟），要改成 `CACHE_NULL_TTL`**（`queryWithPassThrough` 和 `queryWithMutex` 各一处）——改完对着本节把两个理由讲一遍。

### 6.4 布隆过滤器（原理级理解，不实现）

- 结构：一个大 bit 数组 + k 个哈希函数。**写入**：对元素算 k 个哈希，把对应 k 个位置置 1。**查询**：同样算 k 个位置——**只要有一个 0 → 一定不存在**；全 1 → "可能存在"（可能是别的元素置的 1 = 哈希冲突误判）。
- 用于防穿透：数据入库时同步写入布隆过滤器；请求先问过滤器，"一定不存在"直接拒绝，根本不碰 Redis/MySQL。
- 两个天生缺陷：**误判**（只说"可能存在"，绝不会漏杀）；**标准布隆不能删除**（复位一个 bit 会影响共存元素）→ 想删要用计数布隆/布谷鸟过滤器。
- 课程讲义 11.4 有 bitmap 加餐实现，学第九章 bitmap 后可回看。

## 七、缓存雪崩（思路题，无代码）

**定义**：同一时段**大量缓存 key 同时失效**（TTL 集中到期）**或 Redis 服务宕机**，请求全部打到数据库，数据库被冲垮。

| 成因 | 解法 |
|---|---|
| 大量 key 同时过期 | **TTL 加随机值**：`TTL + random(0~5min)`，把过期时间打散 |
| Redis 宕机 | **高可用**：主从 + 哨兵 / Cluster（第八章内容） |
| 请求绕过缓存直击库 | **降级限流**：Sentinel 限流、快速失败、返回默认值 |
| 单层缓存扛不住 | **多级缓存**：本地缓存（Caffeine/Guava）+ Redis 两层 |

【记忆锚点】**穿透是"查不存在的数据"（单点攻击），雪崩是"大量 key 同时失效"（面攻击），击穿是"单个热点 key 失效瞬间"（点攻击）**——三个词发生的前提完全不同，面试先复述前提再答方案。

## 八、缓存击穿：互斥锁 vs 逻辑过期（本模块最难点）

### 8.1 定义与发生前提

**缓存击穿（热点 Key 问题）**：一个**被高并发访问**且**缓存重建业务较复杂**的 key，在**过期失效的瞬间**，无数请求同时 miss、同时回源查库、同时重建——数据库被瞬时打爆。

前提三件套缺一不可：①高并发访问 ②重建复杂（查库慢）③恰好失效瞬间。日常低流量接口不存在击穿问题——**它是一个"流量 × 时机"问题**。

### 8.2 方案一：互斥锁（保证一致性，牺牲可用性）

**思想**：miss 后不许所有人去查库，先抢锁；**抢到的一个人查库重建**，没抢到的睡 50ms 重试（重试时缓存多半已被重建好，直接命中）。

#### tryLock / unlock（你已写好，逐段拆）

```java
private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}

private void unlock(String key) {
    stringRedisTemplate.delete(key);
}
```

- **`setIfAbsent` = Redis 命令 `SET key value NX EX 10`**：NX = **key 不存在才设置**（这是"锁"的语义来源：谁设置成功谁持锁）；携带过期时间是 **NX+EX 一条原子命令**——拿锁和防死锁一步完成，不存在"设置了锁还没来得及设过期就宕机"的窗口。
- **锁自带 10s TTL（`LOCK_SHOP_TTL`）**：持有锁的线程若崩了/卡死了，锁到点自动释放，其他线程最多白等 10 秒——**防死锁**。
- **`BooleanUtil.isTrue(flag)`**：hutool 安全解包。`setIfAbsent` 在连接异常等场景可能返回 null，直接 `flag` 自动拆箱 → NPE。
- **锁的粒度：`lock:shop:{id}`，每个商铺一把锁**——1 号店重建时 2 号店照常并行重建，只有同一个商铺的重建是串行的。如果全局一把锁，所有商品重建排队，性能灾难。
- ⚠️ 初级互斥锁的两个已知缺陷（第六章分布式锁会系统解决，现在留印象）：①**业务没执行完锁先过期** → 别的线程趁虚而入并发重建（缓解：TTL 给够/续期机制/Redisson 看门狗）；②**unlock 无主判断** → 极端情况可能删掉别人的锁（解法：锁值存线程标识，删前校验，且校验+删除要原子 → Lua 脚本）。

#### queryWithMutex 完整版（课程最终形态，照此补完你的代码）

```java
public Shop queryWithMutex(Long id) {
    String key = CACHE_SHOP_KEY + id;
    // 1. 从 redis 查询商铺缓存
    String shopJson = stringRedisTemplate.opsForValue().get(key);
    // 2. 判断是否存在（三分支：真数据 / 空值标记 / 真未命中，和穿透版完全一样）
    if (StrUtil.isNotBlank(shopJson)) {
        return JSONUtil.toBean(shopJson, Shop.class);
    }
    if (shopJson != null) {           // 命中 "" 空值 → 穿透防护
        return null;
    }
    // 4. 缓存重建（互斥锁版只在"真未命中"时多走了锁这一层）
    String lockKey = LOCK_SHOP_KEY + id;    // lock:shop:1
    Shop shop = null;
    try {
        // 4.1 获取互斥锁
        boolean isLock = tryLock(lockKey);
        // 4.2 获取失败 → 休眠后重试
        if (!isLock) {
            Thread.sleep(50);
            return queryWithMutex(id);      // 递归回方法入口 = 重新查缓存
        }
        // 4.3 获取成功 → 查数据库重建
        shop = getById(id);
        // 5. 不存在 → 写空值（穿透防护仍在），返回
        if (shop == null) {
            stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
            return null;
        }
        // 6. 存在 → 写缓存（注意：真数据用 CACHE_SHOP_TTL 30min）
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_SHOP_TTL, TimeUnit.MINUTES);
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    } finally {
        // 7. 无论成败，释放锁
        unlock(lockKey);
    }
    return shop;
}
```

【逐段拆解——每一层为什么】

- **三分支判断原封不动**：互斥锁是**叠加**在穿透方案之上的（击穿和穿透会同时存在），不是替换。
- **重试路径 = 天然 double check**：讲义文字里说"tryLock + double check"，代码里却找不到第二次 get 缓存——因为**休眠重试走递归回到方法入口，入口先 get 缓存**：若持锁线程已完成重建，重试线程直接命中返回，不再查库。这就是 double check，形式藏在"递归回去重新走一遍分支判断"里。
- **正确性的一个隐含不变式：写缓存发生在 unlock 之前**（第 6 步在 try 里，unlock 在 finally 里）。所以**锁一释放，缓存必然已就绪**，后续任何线程都从缓存走——不会出现"锁放了两拨人先后查库"的重复重建。能讲出这句，说明真的读懂了时序。
- **`Thread.sleep(50)`**：等重建完成。重建=查库+写缓存，通常毫秒级，睡 50ms 再重试大概率直接命中。这个值不敏感，太小会空转多次，太大响应变慢。
- **为什么要 try/catch**：`Thread.sleep` 声明抛受检异常 `InterruptedException`，必须处理；课程包装成 RuntimeException 往上抛。
- **为什么 unlock 必须在 finally**：持锁线程若在重建中抛异常，没有 finally 的话锁要等 10s TTL 才释放——期间所有请求睡 50ms→递归→抢锁→再睡，白白空转 10 秒。
- ⚠️ **讲义原版的隐蔽缺陷（2026-11-17 实踩）**：抢锁失败的分支 `return queryWithMutex(id)` 也会触发**本层** finally → `unlock(lockKey)`——等于误删**当前持锁线程**的锁，其他线程趁虚而入并发重建。修法：`Shop shop = null; boolean isLock = false;` 声明在 try 外（顺便解决 try 内声明、try 外 return 看不见的编译错），finally 里 `if (isLock) unlock(lockKey)` 只在拿到过锁时才释放。项目代码已按此修正。
- ⚠️ 课程用**递归**实现重试：重建慢时递归会叠栈（每次 sleep 50ms 才退一层）。**工程化建议改成 `while` 循环 + 重试次数上限**，超限返回失败——这是面试可以主动提的改进点。
- ⚠️ **你当前项目里的 `queryWithMutex` 还是从穿透版复制来的，锁逻辑一行没加**——按上面完整版补：`lockKey`、tryLock 判断、sleep+递归、finally unlock，四处都别漏。

#### 互斥锁方案小结

| 一致性 | 性能 | 实现复杂度 | 额外内存 | 风险 |
|---|---|---|---|---|
| ✅ 强：重建期间只有一个线程碰库，无脏缓存 | ❌ 差：其余线程睡眠等待，并行变串行 | ✅ 简单：一把锁 | ✅ 无 | 锁提前过期并发重建；死锁；递归叠栈 |

### 8.3 方案二：逻辑过期（保证可用性，牺牲一致性）

**思想**：击穿的前提是"物理 TTL 到期失效"。那就**不设物理 TTL**，把过期时间作为字段**存进 value 里自己判断**——物理上 key 永不过期、缓存永远命中，"过期"只是业务层面的标记；发现逻辑过期后，**拿锁的线程开独立线程异步重建，所有线程（包括拿锁失败的）立刻返回旧数据**。

#### 前置一：RedisData 包装类（不改实体的无侵入方案）

```java
@Data
public class RedisData {
    private LocalDateTime expireTime;
    private Object data;
}
```

value 结构变成：`{"expireTime":"...", "data":{...shop...}}`。不往 Shop 实体里塞 expireTime 字段（污染实体），用包装类包一层。

#### 前置二：缓存预热（没有这步整个方案跑不起来！）

逻辑过期版的 key **物理永不过期、miss 不查库**——数据必须在**上线前灌进去**。课程用单元测试预热：

```java
public void saveShop2Redis(Long id, Long expireSeconds) {
    // 1. 查询店铺数据
    Shop shop = getById(id);
    // 2. 封装逻辑过期
    RedisData redisData = new RedisData();
    redisData.setData(shop);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));
    // 3. 存入 redis —— 注意：不设物理 TTL！
    stringRedisTemplate.opsForValue().set(CACHE_SHOP_KEY + id, JSONUtil.toJsonStr(redisData));
}

// 测试类里：saveShop2Redis(1L, 10L);   // 10 秒后逻辑过期，方便观察重建
```

#### 正式代码

```java
private static final ExecutorService CACHE_REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);

public Shop queryWithLogicalExpire(Long id) {
    String key = CACHE_SHOP_KEY + id;
    // 1. 从 redis 查询商铺缓存
    String json = stringRedisTemplate.opsForValue().get(key);
    // 2. 未命中 → 直接返回 null（不查库！预热型方案，冷数据不归它管）
    if (StrUtil.isBlank(json)) {
        return null;
    }
    // 3. 命中 → 反序列化：先整体转 RedisData，再把 data 二次转 Shop
    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    Shop shop = JSONUtil.toBean((JSONObject) redisData.getData(), Shop.class);
    LocalDateTime expireTime = redisData.getExpireTime();
    // 4. 未过期 → 直接返回
    if (expireTime.isAfter(LocalDateTime.now())) {
        return shop;
    }
    // 5. 已逻辑过期 → 尝试拿锁，异步重建
    String lockKey = LOCK_SHOP_KEY + id;
    boolean isLock = tryLock(lockKey);
    if (isLock) {
        // 5.1 拿到锁 → 开独立线程池异步重建，当前线程不等
        CACHE_REBUILD_EXECUTOR.submit(() -> {
            try {
                this.saveShop2Redis(id, CACHE_SHOP_TTL * 60);   // 重建：重查库+重包逻辑过期
            } catch (Exception e) {
                throw new RuntimeException(e);
            } finally {
                unlock(lockKey);                                 // 重建完在异步线程里放锁
            }
        });
    }
    // 6. 无论拿没拿到锁 → 立刻返回旧数据
    return shop;
}
```

【逐段拆解】

- **miss 为什么用 `isBlank` 且直接返回 null、不查库**：这是**预热型方案**的契约——"这个 key 的数据理应早就被灌进去了"，miss 说明根本不是热点数据，不该由本方案兜底查库（都查库了还谈什么防击穿）。注意和穿透版的**三分支**不同：逻辑过期版**不做穿透防护**（它压根不回源），所以一层 `isBlank` 就够。
- **为什么要两次 toBean**：JSON 先整体反序列化成 `RedisData`，此时 `data` 字段是 `JSONObject`（JSON 库不知道它该是 Shop），**必须二次 toBean 指定目标类型**——嵌套对象反序列化不会自动落到实体类。
- **拿锁成功 → 独立线程池重建**：重建业务（查库）耗时，不能占用用户请求线程；固定 10 线程的池限制并发重建数。**锁的释放发生在异步线程的 finally 里**——重建没完成，锁一直被异步线程持有。
- **拿锁失败 → 什么也不做，直接返回旧数据**：说明已经有线程在重建了，我等着没意义，旧数据先顶着。
- **重建完成的瞬间之前，所有人拿到的都是旧数据**——这就是"短暂脏数据窗口"，是本方案用一致性换可用性的全部代价。
- **为什么异步重建还要加锁**：防止同一瞬间多个线程都发现过期、都开线程重复查库重建——锁保证"同一时刻只有一个重建任务在跑"。
- **兜底追问——异步线程崩了锁怎么办**：tryLock 自带 10s TTL，锁不会永久卡死；重建失败则旧数据继续顶着到下次触发，可用性不受影响。

#### 互斥锁 vs 逻辑过期 对比（面试必背）

| 维度 | 互斥锁 | 逻辑过期 |
|---|---|---|
| 一致性 | ✅ 强，无脏读 | ❌ 弱，重建完成前返回旧数据 |
| 可用性/性能 | ❌ 差，线程睡眠等待 | ✅ 好，永不等待，立刻响应 |
| 实现复杂度 | ✅ 简单 | ❌ 复杂（RedisData/预热/线程池/异步放锁） |
| 额外内存 | ✅ 无 | ❌ expireTime + 包装层 |
| 前提条件 | 无 | **必须预热**，物理 key 永不过期 |
| 适用场景 | 一致性敏感、重建不频繁 | **热点活动数据**（如秒杀商品），可用性敏感 |

**口述版**："互斥锁保证一致但让人等，逻辑过期保证不等但有短暂脏数据——本质是 CAP 里一致性 vs 可用性的取舍；我们的商户详情用互斥锁就够，秒杀商品这类热点可用性优先，会选逻辑过期。"

## 十、封装 CacheClient 工具类（✅ 2026-11-18 完成，首版 5 个 bug 已修复，见 10.4）

### 10.1 为什么要封装

到击穿为止，`queryWithPassThrough / queryWithMutex / queryWithLogicalExpire` 三个方法 90% 代码相同（get → 分支判断 → 回写），差别只在"防什么问题"。耦合在 ShopServiceImpl 里意味着 Blog、Voucher 每个实体都要复制一遍 → **把骨架抽成通用工具类，业务差异用参数传进去**。

四个方法的需求（讲义原文）：

1. `set`：任意对象序列化存 String key，**带 TTL** —— 普通"写缓存"
2. `setWithLogicalExpire`：存对象 + **逻辑过期时间**（不设物理 TTL）—— 逻辑过期的"写"
3. `queryWithPassThrough`：泛型查询，**空值缓存防穿透**
4. `queryWithLogicalExpire` / `queryWithMutex`：泛型查询，**逻辑过期/互斥锁防击穿**

### 10.2 泛型方法签名拆解（本节知识总验收，接住第三节）

```java
public <R, ID> R queryWithPassThrough(
        String keyPrefix,      // 业务前缀：CACHE_SHOP_KEY / CACHE_XXX_KEY（工具类不该写死业务）
        ID id,                 // 标识类型不锁定：Long/Integer/String 都能传
        Class<R> type,         // 反序列化目标类型（JSON 不知道 R 是什么，运行时传进来）
        Function<ID, R> dbFallback,  // "怎么查数据库"作为行为参数传入
        Long time, TimeUnit unit) {  // 真数据的 TTL
```

- **`Function<ID, R> dbFallback`** = 第三节 `Function<T,R>` 的实战：`id 进 → 实体出`。调用方传 `this::getById`（方法引用）——工具类**不依赖任何具体 Service**，Shop/Blog/User 通吃。这就是"行为参数化"：数据当参数人人会，**行为当参数才解耦**。
- **`Class<R> type`**：泛型擦除后运行时拿不到 R 的 Class，`JSONUtil.toBean(json, type)` 必须显式传入。
- 调用端一行：`cacheClient.queryWithPassThrough(CACHE_SHOP_KEY, id, Shop.class, this::getById, CACHE_SHOP_TTL, TimeUnit.MINUTES);` —— 原来三个方法的业务从此各一行。

### 10.3 完整代码（课程版，学到时对照抄）

```java
@Slf4j
@Component
public class CacheClient {

    private final StringRedisTemplate stringRedisTemplate;
    private static final ExecutorService CACHE_REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);

    public CacheClient(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    // 方法1：普通写（带 TTL）
    public void set(String key, Object value, Long time, TimeUnit unit) {
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(value), time, unit);
    }

    // 方法2：逻辑过期写（物理不设 TTL，过期时间包在 value 里）
    public void setWithLogicalExpire(String key, Object value, Long time, TimeUnit unit) {
        RedisData redisData = new RedisData();
        redisData.setData(value);
        redisData.setExpireTime(LocalDateTime.now().plusSeconds(unit.toSeconds(time)));
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(redisData));
    }

    // 方法3：防穿透（空值缓存）—— 和 6.3 的方法逐行同构，只是 R/ID 泛型化 + dbFallback 参数化
    public <R, ID> R queryWithPassThrough(
            String keyPrefix, ID id, Class<R> type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
        String key = keyPrefix + id;
        String json = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isNotBlank(json)) {
            return JSONUtil.toBean(json, type);
        }
        if (json != null) {           // 空值标记
            return null;
        }
        R r = dbFallback.apply(id);   // ← 原来的 getById(id) 换成了回调
        if (r == null) {
            stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
            return null;
        }
        this.set(key, r, time, unit);
        return r;
    }

    // 方法4：互斥锁防击穿 —— 和 8.2 同构，锁前缀见 ⚠️
    public <R, ID> R queryWithMutex(
            String keyPrefix, ID id, Class<R> type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
        String key = keyPrefix + id;
        String shopJson = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isNotBlank(shopJson)) {
            return JSONUtil.toBean(shopJson, type);
        }
        if (shopJson != null) {
            return null;
        }
        String lockKey = LOCK_SHOP_KEY + id;    // ⚠️ 见下方改进点
        R r = null;
        try {
            boolean isLock = tryLock(lockKey);
            if (!isLock) {
                Thread.sleep(50);
                return queryWithMutex(keyPrefix, id, type, dbFallback, time, unit);
            }
            r = dbFallback.apply(id);
            if (r == null) {
                stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
                return null;
            }
            this.set(key, r, time, unit);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        } finally {
            unlock(lockKey);
        }
        return r;
    }

    // 方法5：逻辑过期防击穿 —— 和 8.3 同构
    public <R, ID> R queryWithLogicalExpire(
            String keyPrefix, ID id, Class<R> type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
        String key = keyPrefix + id;
        String json = stringRedisTemplate.opsForValue().get(key);
        if (StrUtil.isBlank(json)) {
            return null;
        }
        RedisData redisData = JSONUtil.toBean(json, RedisData.class);
        R r = JSONUtil.toBean((JSONObject) redisData.getData(), type);
        LocalDateTime expireTime = redisData.getExpireTime();
        if (expireTime.isAfter(LocalDateTime.now())) {
            return r;
        }
        String lockKey = LOCK_SHOP_KEY + id;    // ⚠️ 同上
        boolean isLock = tryLock(lockKey);
        if (isLock) {
            CACHE_REBUILD_EXECUTOR.submit(() -> {
                try {
                    R newR = dbFallback.apply(id);
                    this.setWithLogicalExpire(key, newR, time, unit);
                } catch (Exception e) {
                    throw new RuntimeException(e);
                } finally {
                    unlock(lockKey);
                }
            });
        }
        return r;
    }

    private boolean tryLock(String key) {
        Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
        return BooleanUtil.isTrue(flag);
    }

    private void unlock(String key) {
        stringRedisTemplate.delete(key);
    }
}
```

【改进点（写简历/面试主动提）】
- ⚠️ **锁前缀写死 `LOCK_SHOP_KEY`（shop 专属）**：通用工具类里锁 key 应该也作为参数传入（如 `String lockPrefix`），否则查 Blog 的缓存也去抢 shop 的锁名空间——课程为省事写死，一眼能看出"工具类通用性破功"，指出这一点比会背代码值钱。
- 逻辑过期版同样**要求预热**（`setWithLogicalExpire` 先灌数据），别学完就忘契约。

### 10.4 实战复盘：首版 CacheClient 的 5 个 bug（2026-11-18，全部修复）

| # | bug | 后果 | 正确姿势 |
|---|---|---|---|
| 1 | `setWithLogicalExpire` 写了物理 TTL | 30s 后 key 被 Redis 删掉 → miss → "店铺不存在" | **逻辑过期物理不设 TTL**，过期信息只在 value 的 expireTime 里——方案灵魂，物理 TTL 和逻辑过期互斥 |
| 2 | `setWithLogicalExpire` 参数写成 `String value` | 泛型 R 传不进去（编译错） | `Object value` + 内部 `toJsonStr` |
| 3 | `queryWithPassThrough` 回写误用 `setWithLogicalExpire` | 下次读到 `{expireTime, data:{...}}` 包装 JSON，硬转 Shop **全字段 null** | 普通回写用 `set(key, r, time, unit)` |
| 4 | `dbFallback` 传了 `this::queryById` | **无限递归**：重建线程调 queryById → 又触发逻辑过期 → 又开重建线程…… | `this::getById`——回调必须是"最里层纯查库"动作，不能带缓存逻辑 |
| 5 | `CACHE_SHOP_TTL`(30) 配了 `TimeUnit.SECONDS` | 30 秒就逻辑过期，不停重建 | 数值和单位要一起看，`MINUTES` |

另有两处连带：`queryById` 写成 `CacheClient.queryWithLogicalExpire(...)`（静态式调用实例方法，编译错 → `cacheClient.`）；lockKey 写死 `CACHE_SHOP_KEY`（→ `keyPrefix + id`，见上方改进点）。

【温馨小贴士】#4 是最阴的一个：编译能过、正常路径可能也跑得通，只在"过期触发重建"这个低频分支里才炸——**最危险的 bug 都藏在低频分支**，测逻辑过期必须等过期那一刻。

## 十三、面试题库

> 每题先背"一句话版"，再展开要点。标准：不看答案口述 2 分钟。

### 🔥 必背五题

**Q1：缓存穿透、击穿、雪崩分别是什么？怎么解决？**
- 一句话版："穿透是查缓存和库都不存在的数据，用空值缓存或布隆过滤器；击穿是单个热点 key 失效瞬间高并发回源，用互斥锁或逻辑过期；雪崩是大量 key 同时失效或 Redis 宕机，用 TTL 加随机值、集群高可用、限流降级、多级缓存。"
- 展开：先说**发生前提**（三者前提完全不同），再方案；主动带一句本项目的落地（空值 2min / queryWithMutex / TTL 可加随机）。

**Q2：缓存和数据库的一致性怎么保证？为什么先更新数据库再删缓存？**
- 一句话版："主动更新 + 超时剔除兜底；顺序上先库后缓存——先删缓存的方案在并发下窗口大、脏得久，先库后缓存的脏窗口要求'读回写比写库删缓存还慢'，概率极低，再靠 TTL 做最后防线。"
- 展开：三策略表（内存淘汰/超时剔除/主动更新）→ 删除 vs 更新（懒加载，防无效写）→ 两张时序图 → 承认理论窗口 + 概率分析 + TTL 兜底 → 延伸：删缓存失败可用消息队列重试 / canal 订阅 binlog 异步删。

**Q3：为什么删除缓存而不是更新缓存？**
- 一句话版："更新缓存是每次写都同步写，写多读少时大量更新白费（没人读）；删除是懒加载，等真有读请求才重建，写路径只花一次 DELETE，且并发写不会把缓存写花。"
- 展开：反例场景（写少读多且下次必读）更新才占优 → 说明懂权衡，不是背教条。

**Q4：互斥锁怎么实现的？有什么问题？**
- 一句话版："用 Redis 的 SETNX 语义——`setIfAbsent(key, v, 10, SECONDS)` 一条原子命令完成拿锁+设过期，拿到锁的线程查库重建，没拿到的睡 50ms 递归重试，重试回入口先查缓存（天然 double check），finally 里释放锁。"
- 展开缺陷：锁提前过期→并发重建（续期/Redisson 看门狗）；unlock 无主校验→可能删别人的锁（锁值带线程标识 + Lua 原子校验删除）——第六章分布式锁逐一解决，现在能点到即加分。

**Q5：逻辑过期为什么能防击穿？代价是什么？**
- 一句话版："物理 key 永不过期、永远命中，过期时间存 value 里自己判断；发现过期后拿锁的线程开独立线程池异步重建，**所有线程立刻返回旧数据**——用短暂脏数据换掉所有等待，代价是弱一致 + 必须预热 + 实现复杂。"
- 展开：RedisData 包装（无侵入）→ miss 不查库（预热契约）→ 异步重建 + 异步放锁 → 两方案对比表收尾。

### ⚡ 追问链

**Q6：空值缓存的 TTL 为什么要短？**
空值不是数据是占位标记：①防内存被恶意 id 的空 key 堆满；②**短期不一致的时长 = 空值 TTL**——库上新增该数据后最多 2 分钟不可见，2 分钟是"防护效果 vs 自愈速度"的权衡。

**Q7：布隆过滤器原理？为什么有误判、为什么不能删？**
bitmap + k 个哈希，写入置 1 查询验 1；全 1 只能说"可能存在"（别的元素置的 1 = 哈希冲突），有 0 则"一定不存在"；删除会把共位元素的标记抹掉 → 计数布隆/布谷鸟过滤器可解。

**Q8：详情用 String 存 JSON，登录用户用 Hash，为什么不一样？**
整体读写的对象用 String（一次 toJsonStr/toBean 最简单）；需要字段级读写的用 Hash。商户详情没有字段级修改诉求；登录用户要"活跃续期 + 可能改字段"。

**Q9：删缓存失败怎么办？**
同步重试 → 消息队列异步重试 → canal 订阅 MySQL binlog 删缓存（把"删"变成 binlog 驱动，业务零侵入）。分层答，先说课程方案，再延伸。

**Q10：TTL 你们怎么定的？**
真数据 30min（业务容忍度 + 重建成本权衡）、空值 2min（不一致窗口）、锁 10s（大于重建耗时，防死锁）；可主动提"30min 可加随机值防雪崩"。
