## 〇、模块全景与全链路时序

### 0.1 缓存三段式（Cache Aside，本模块所有代码的骨架）

```
请求进来
   │
   ├─ ① 查 Redis ────── 命中 ──→ ② 反序列化直接返回（不碰数据库）
   │
   └─ 未命中
        │
        ├─ ③ 查 MySQL
        ├─ ④ 库里也没有 → 返回错误（正式防穿透方案在本章后文）
        └─ ⑤ 查到了 → 写回 Redis（下次命中）→ 返回
```

**一句话总结**：数据库是数据的唯一权威版本，Redis 只是它的"读放大镜"；读先走缓存，未命中才回源，回源后回写。**牺牲写后的短暂不一致（配合更新策略），换取读性能。**

## 一、商铺类型缓存：课程官方 String 版（骨架版）

课程视频的标准写法，**一个 key 存整包 JSON**：

```java
public Result queryTypeList() {
    // 1. 从 Redis 查询商铺缓存
    String shopTypeJson = stringRedisTemplate.opsForValue().get(CACHE_SHOP_TYPE_KEY);
    // 2. 判断是否存在
    if (StrUtil.isNotBlank(shopTypeJson)) {
        // 3. 存在 → 反序列化直接返回
        return Result.ok(JSONUtil.toList(shopTypeJson, ShopType.class));
    }
    // 4. 不存在 → 查数据库（MP：ORDER BY sort ASC）
    List<ShopType> shopTypes = query().orderByAsc("sort").list();
    // 5. 库里也没有 → 返回错误
    if (CollectionUtil.isEmpty(shopTypes)) {
        return Result.fail("分类不存在");
    }
    // 6. 写回缓存（整包一次序列化）
    stringRedisTemplate.opsForValue().set(CACHE_SHOP_TYPE_KEY, JSONUtil.toJsonStr(shopTypes));
    // 7. 返回
    return Result.ok(shopTypes);
}
```

【拆解】
- **三段式一目了然**：get → miss 查库 → set 回写。第一遍学就写这个版本，把骨架刻进肌肉记忆。
- **`StrUtil.isNotBlank` 而不是 `!= null`**：Redis get 对不存在的 key 返回 null，但判 blank 还顺带覆盖空串 `""`——这是给后文**空值缓存防穿透留的口子**（把空值存成 `""`，下次 blank 判断直接 miss 掉恶意 key，学到穿透那节回头看这行会有第二次收获）。
- **单 key 整包**：写入 `JSONUtil.toJsonStr(整个 List)`，读取一次 `toList`。优点：一次序列化/一次反序列化、一个 key 好管理；缺点：改一条要整包覆盖、无字段粒度。
- key：`cache:shopType:`（`RedisConstants.CACHE_SHOP_TYPE_KEY`），课程此场景**没设 TTL**——数据几乎不变 + 是"预热型"数据；面试被问就说"建议补 TTL + 更新时删缓存"。

## 二、List 版实现逐段讲解（CSDN 参考版，opsForList 练手）

> 来源：CSDN「Purse Wind」黑马点评笔记（原文见参考资料）。**它和官方版的区别**：把整包 JSON 换成 Redis List 的 N 个元素，每个元素是一条 ShopType 的 JSON——顺带把 List 类型的命令全练了一遍。

### 2.1 读缓存

```java
List<String> shopTypeJson = stringRedisTemplate.opsForList().range(key, 0, -1);
if (CollectionUtil.isNotEmpty(shopTypeJson)) { ... }
```

- `opsForList().range(key, 0, -1)` = 命令 **`LRANGE key 0 -1`**：取下标 0 到 -1 的全部元素。**两个下标都是闭区间**，`-1` = 最后一个元素（`-2` = 倒数第二）。
- 返回 `List<String>`：Redis List 每个元素本质是字符串，我们存的是一条条 JSON。
- ⚠️ **key 不存在时返回空 List，不是 null**（LRANGE 对不存在的 key 返回空数组）。所以判空必须用 `CollectionUtil.isNotEmpty()`（对 null 和空集合都返回 false）；写 `!= null` 等于没写。

### 2.2 命中分支

```java
List<ShopType> shopTypes = JSONUtil.toList(shopTypeJson.toString(), ShopType.class);  // ⚠️ 歪写法，见 2.5
Collections.sort(shopTypes, (o1, o2) -> o1.getSort() - o2.getSort());                 // ⚠️ 多余，见 2.4
return Result.ok(shopTypes);
```

### 2.3 未命中分支 + 回写

```java
// 查库，读出时已按 sort 升序
List<ShopType> shopTypes = query().orderByAsc("sort").list();
if (CollectionUtil.isEmpty(shopTypes)) {
    return Result.fail("商铺类型不存在...");
}
// 每个元素单独转 JSON（List 类型的粒度是"元素"，不能整包一起转）
List<String> shopTypesJson = shopTypes.stream()
        .map(shopType -> JSONUtil.toJsonStr(shopType))
        .collect(Collectors.toList());
// 从右边进队保序
stringRedisTemplate.opsForList().rightPushAll(key, shopTypesJson);
return Result.ok(shopTypes);
```

### 2.4 ★ rightPushAll 保序原理（本段精华，想通它就知道 2.2 的 sort 是废话）

```
rightPushAll(key, [A, B, C])        leftPushAll(key, [A, B, C])
  A →  [A]                             A →  [A]
  B →  [A B]                           B →  [B A]
  C →  [A B C] ✅ 与库里顺序一致         C →  [C B A] ❌ 整体反序
```

- 库里 `ORDER BY sort` 有序读出 → **逐个从右边进队**（RPUSH，先进队在左）→ Redis 里从左到右仍升序 → `range(0,-1)` 从左往右取，**天然有序**。
- `leftPushAll` 是逐个从左进（LPUSH），整批进完顺序正好颠倒。
- 所以命中路径上 `range` 拿到的本来就是升序，`Collections.sort` 那行**删掉毫无影响**——能自己发现这点，才算真懂 List 的顺序。**这就是"读有序"和"写有序对齐"：写入顺序 = 读取顺序，中间不需要再排。**

### 2.5 这份代码的 3 个问题（读懂 ≠ 照抄）

| # | 问题 | 为什么是问题 | 改法 |
|---|---|---|---|
| 1 | `shopTypeJson.toString()` 再 toList | `ArrayList.toString()` 输出 `[a, b, c]`，**恰好长得像 JSON 数组**才被解析成功——依赖巧合：可读性差，还要先把整个大 List 拼成一根巨型字符串 | 逐个反序列化，与写入路径对称：`shopTypeJson.stream().map(json -> JSONUtil.toBean(json, ShopType.class)).collect(toList())` |
| 2 | 命中后又 `Collections.sort` | rightPush 已保序（见 2.4），纯多余 | 删 |
| 3 | 没设 TTL | 缓存永不失效，和官方版一样欠妥 | 补 `expire(key, CACHE_SHOP_TYPE_TTL, TimeUnit.MINUTES)` |
| 附 | 减法比较 `o1.getSort()-o2.getSort()` | 极端值溢出（`Integer.MIN_VALUE - 1` 翻正）；本项目 sort 很小无碍，但写法要升级 | `Comparator.comparingInt(ShopType::getSort)` 或 `Integer.compare` |

### 2.6 改进版完整代码（建议照这个写进项目）

```java
String key = CACHE_SHOP_TYPE_KEY;
// 1.查缓存（key 不存在 → 空 List，不是 null）
List<String> typeJsonList = stringRedisTemplate.opsForList().range(key, 0, -1);
// 2.命中：逐个反序列化（List 天然有序，无需再 sort）
if (CollectionUtil.isNotEmpty(typeJsonList)) {
    List<ShopType> list = typeJsonList.stream()
            .map(json -> JSONUtil.toBean(json, ShopType.class))
            .collect(Collectors.toList());
    return Result.ok(list);
}
// 3.未命中查库（读出已按 sort 升序）
List<ShopType> shopTypes = query().orderByAsc("sort").list();
if (CollectionUtil.isEmpty(shopTypes)) {
    return Result.fail("商铺类型不存在");
}
// 4.回写：逐个序列化 → 从右进队保序 → 设 TTL
List<String> jsonList = shopTypes.stream()
        .map(JSONUtil::toJsonStr)
        .collect(Collectors.toList());
stringRedisTemplate.opsForList().rightPushAll(key, jsonList);
stringRedisTemplate.expire(key, CACHE_SHOP_TYPE_TTL, TimeUnit.MINUTES);
// 5.返回
return Result.ok(shopTypes);
```

⚠️ 另一个只有 List 版有的坑：**想用"存空 List"防穿透是不行的**——Redis 空 list 会被自动删除 key，且 RPUSH 空集合直接报错；穿透防护得靠 String 版的空值缓存或布隆过滤器（后文）。

### 2.7 String 版 vs List 版取舍（面试口述）

| 维度 | String 整包（官方） | List 分元素（CSDN） |
|---|---|---|
| 读写开销 | 一次序列化/反序列化 | N 次小转换，但每次粒度小 |
| 修改成本 | 改一条 = 整包覆盖 | 可按元素定位操作 |
| 保序 | 靠序列化顺序 | **结构天然保序**（RPUSH 进队顺序） |
| 空值缓存防穿透 | ✅ 存 `""` 即可 | ❌ 空 list 自动删 key，做不到 |
| 适用场景 | 小且少变的整包数据（本场景就是） | 需要元素级操作/分页的列表 |

**口述版**："商铺类型又小又稳定，String 整包最简单，官方版就够；List 版的价值是练类型、且天然保序，但它没法存空值做穿透防护——数据结构选型要连着后面的缓存问题一起权衡。"

## 三、Lambda & Stream 补课（Java 基础八股结合点）

### 3.1 Lambda 本质：函数式接口的实例

**函数式接口** = 只有一个抽象方法的接口（可加 `@FunctionalInterface` 让编译器检查）。`Comparator` 就是：

```java
@FunctionalInterface
public interface Comparator<T> {
    int compare(T o1, T o2);   // 唯一抽象方法
}
```

Lambda 就是这个接口的实例："参数 -> 方法体"。排序写法的三代演进：

```java
// ① 匿名内部类（史前，5 行）
Collections.sort(list, new Comparator<ShopType>() {
    @Override
    public int compare(ShopType o1, ShopType o2) { return o1.getSort() - o2.getSort(); }
});
// ② Lambda（1 行，参数类型靠推断）
Collections.sort(list, (o1, o2) -> o1.getSort() - o2.getSort());
// ③ 方法引用（地道写法）
list.sort(Comparator.comparingInt(ShopType::getSort));
```

**`compare` 返回值约定（要背）**：负数 → o1 在前；0 → 相等不动；正数 → o2 在前。所以 `o1.getSort() - o2.getSort()` = 升序。减法会溢出，稳写 `Integer.compare(o1, o2)`。

呼应登录模块：`setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString())` 也是 Lambda，类型是 `BiFunction<String, Object, Object>`——同一个知识点。

### 3.2 Stream 流水线：三段结构 + 等价循环

```java
shopTypes.stream()                                    // ① 源：上流水线
        .map(shopType -> JSONUtil.toJsonStr(shopType)) // ② 中间操作：逐个转换（惰性，只记账）
        .collect(Collectors.toList());                 // ③ 终结操作：真正执行，装车返回
```

看不懂就翻译成普通循环，**语义完全等价**：

```java
List<String> jsonList = new ArrayList<>();
for (ShopType shopType : shopTypes) {
    jsonList.add(JSONUtil.toJsonStr(shopType));
}
```

- 常用中间操作：`map`（一对一转换）、`filter`（元素 -> boolean 过滤）、`sorted`；**惰性**：中间操作只是记流水账，终结操作（collect/forEach）一锤定音才执行。
- 本次用到的 `map()` 的参数类型是 **`Function<T,R>`**（有进有出）。

### 3.3 四大内置函数式接口（认脸版）

| 接口 | 签名 | 一句话 | 用在哪 |
|---|---|---|---|
| `Supplier<T>` | `() -> T` | 无进有出（工厂） | `orElseGet(Supplier)` |
| `Consumer<T>` | `T -> ()` | 有进无出（消费） | `forEach` |
| `Function<T,R>` | `T -> R` | 有进有出（转换） | **stream `map`** |
| `Predicate<T>` | `T -> boolean` | 判断真假 | stream `filter` |

### 3.4 笔记里那个疑问的答案

"想用 `BeanUtil.copyToList` + `CopyOptions.setFieldValueEditor`" → 不行：`copyToList` 是 **bean → bean** 拷贝，`setFieldValueEditor` 是 `beanToMap`（bean → Map）的编辑器；而本场景要的是 **bean → JSON 字符串**，根本不是一条赛道。stream + `toJsonStr` 就是正确工具，别硬套登录模块的写法。
