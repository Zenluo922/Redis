## 二、分布式锁实现思路（ch4.1~4.2）

**需求回顾**：集群下 synchronized 只能锁住一个 JVM（03 篇第七节），要跨机器互斥，锁必须放在**所有机器都看得见的公共位置**——Redis 是天然选择（本项目本来就用它）。

**用 Redis 实现一把合格的锁，三个条件对应三条命令**：

| 条件 | 白话 | Redis 实现 |
|---|---|---|
| 互斥 | 一把钥匙只有一个人能拿 | `SETNX`（key 不存在才设置成功 → 抢到锁） |
| 防死锁 | 拿到钥匙的人断电了，钥匙不能永远卡在锁里 | `SET key val EX seconds`（过期时间兜底） |
| 安全释放 | 只能拆自己贴的条，不能撕别人的 | 锁值存"加锁者标识"，释放前核对 |

## 三、版本一：tryLock + unlock（ch4.3）

```java
// 加锁：一条命令 = SETNX + EXPIRE 的原子合并版
Boolean success = stringRedisTemplate.opsForValue()
        .setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
return Boolean.TRUE.equals(success);   // 自动拆箱有风险，用 equals 判

// 释放：finally 里删 key（保证业务抛异常也释放）
```

**三个关键点**：

1. **必须一条命令带过期时间**。反面教材：`setIfAbsent(k, v)` 成功后再单独 `expire(k, 10)`——两条命令之间宕机 → 锁永远不过期 → **死锁**（钥匙断在锁里，所有人等一年）。Spring 的 `setIfAbsent(key, val, timeout, unit)` 底层就是 `SET key val NX EX seconds` 一条命令。
2. **unlock 放 finally**：业务代码抛异常时锁也能释放，否则只能等 TTL 兜底（期间业务全阻塞）。
3. **返回值用 `Boolean.TRUE.equals()` 接**：返回值是包装类型 Boolean，直接拆箱给 boolean，null 时 NPE。

## 四、误删问题（ch4.4~4.5）

### 4.1 场景时间线（白话：撕了别人的贴条）

```
线程1: setnx 加锁成功（TTL 10s）→ 执行业务 → 【FULL GC / 网络卡，卡了 10s+】
       ……锁的 10s TTL 到期，Redis 自动删除（锁"丢了"）
线程2: setnx 成功（拿到的是"新锁"）→ 开始执行业务
线程1: GC 醒来 → finally 里 delete → ❌ 删掉的是线程2的锁！
线程3: setnx 成功 → 线程2、3 同时执行业务 ❌ 互斥失效
```

### 4.2 改进：锁值存线程标识，释放前先核对

```java
private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";
```

- **为什么是 `UUID + threadId` 拼接**：threadId 只在**单个 JVM 内**唯一——两台 Tomcat 各自都有线程 5，单用 threadId 会撞；UUID 每个 JVM 启动时生成一个全局唯一前缀，拼上 threadId 后标识变成"哪台 JVM 的哪个线程"，绝对唯一。
- **为什么 `toString(true)`**：Hutool 的 UUID 传 `true` 返回不带横线的串（横线在 Redis 值里没有意义还占字节）。

> 🅱️ **与原文差异（2026-11-22 真实爆红）**：这里必须 import **Hutool 的 `cn.hutool.core.lang.UUID`**——`toString(boolean)` 是它特有的方法；JDK 的 `java.util.UUID.toString()` 不接收参数。IDEA 自动导包时两个 UUID 都会弹出来，选错直接编译爆红。详见踩坑表 #1。

改进后的 unlock（先判断再删）：

```java
public void unlock() {
    String threadId = ID_PREFIX + Thread.currentThread().getId();
    String id = stringRedisTemplate.opsForValue().get(KEY_PREFIX + name);
    if (threadId.equals(id)) {
        stringRedisTemplate.delete(KEY_PREFIX + name);   // ⚠️ 此版本有缝隙，见第五节
    }
}
```

## 五、改进版的缺口："判断 + 删除"不原子（ch4.6）

### 5.1 时间线推演

```
线程1: get → 标识匹配 ✅（"是我的锁"）→ 【恰好此刻阻塞：GC / 网络抖动】
       ……锁 TTL 到期自动删除
线程2: setnx 成功（新锁）
线程1: 醒来 → delete → ❌ 又删了线程2的锁
```

**微妙之处**：判断通过的那一刻"锁是我的"没说错；错在**判断和删除之间隔了一次网络往返**，这期间锁可能已经不是我的了。`equals` 判断做了等于没做——它校验的是"过去"，保护不了"未来"。

### 5.2 为什么 03 篇的思路在这里走不通

| | 03 篇超卖 | 本节的锁释放 |
|---|---|---|
| 缝隙 | "查库存 + 扣减"两步 | "查标识 + 删锁"两步 |
| 缝合手段 | 数据库 update **自带行锁**，把判断缝进动作（`where stock > 0`） | Redis 的 get / delete 是两条**独立命令**，没有任何机制缝合 |
| 能否把条件塞进一条命令？ | ✅ update 带条件是 SQL 本来就支持的 | ❌ delete 不支持"仅当值等于 X 才删"（Redis 6.2 之前没有 CAS 语义的删除） |

**MULTI/EXEC（Redis 事务）为什么救不了**：MULTI 只是把命令打包排队依次执行，**命令入队时就必须完全确定**，不能写"如果 get 的结果是我的标识，才 del"——它没有分支逻辑，做不到"后一条依赖前一条的结果"。

**结论**：要么 Redis 原生提供"条件删除"，要么把整段逻辑塞进**一条命令**里执行 → Lua 脚本。

## 六、Lua 脚本：判断+删除原子化 ★ 本篇核心（ch4.7~4.8）

### 6.1 Lua 是什么，Redis 怎么执行它

- Lua 是一门轻量脚本语言，**Redis 2.6 起内置了 Lua 解释器**——脚本跟着 Redis 走，客户端不需要装任何 Lua 环境。
- 核心机制一句话：**Redis 把整段脚本当作一条命令执行**。Redis 单线程处理命令，脚本执行期间不会插入任何其他客户端的命令 → 脚本里写 3 条还是 30 条命令，对外都是一个**不可分割的整体** → 天然原子。

**白话比喻**：Redis 是只有**一个窗口**的银行。平时你每办一笔业务都要取一次号（一条命令），号与号之间谁都可能插队；Lua 就是把"查余额 → 判断够不够 → 转账"写在**同一张申请单**上，一次性递进窗口——柜员办完这一单才叫下一个号，中间没人能插进来。

### 6.2 脚本逐行精讲（`resources/unlock.lua`）

```lua
-- 获取锁中的线程标示（redis.call：在脚本里执行 Redis 命令）
local id = redis.call('get', KEYS[1])
-- 比较线程标示与锁中的标示是否一致
if (id == ARGV[1]) then
    -- 一致，释放锁（del 返回删除的条数：1 = 删成功）
    return redis.call('del', KEYS[1])
else
    -- 不一致，说明锁不是自己的（可能已过期被别人拿走），不释放
    return 0
end
```

**KEYS / ARGV 占位符**：key 和参数**不写死在脚本里**，调用时从外面传进来。两个好处：① 脚本内容固定 → Redis 可以按 SHA1 缓存复用；② Redis Cluster 下脚本只能访问同一个 slot 的 key，key 外置才能正确路由。

### 6.3 Java 调用（`SimpleRedisLock` 当前版完整代码）

```java
public class SimpleRedisLock implements ILock {
    private String name;
    private StringRedisTemplate stringRedisTemplate;

    public SimpleRedisLock(String name, StringRedisTemplate stringRedisTemplate) {
        this.name = name;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    private static final String KEY_PREFIX = "lock:";
    private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";

    // 加载 classpath 下的 unlock.lua，结果类型为 Long（0/1）
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
    static {
        UNLOCK_SCRIPT = new DefaultRedisScript<>();
        UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
        UNLOCK_SCRIPT.setResultType(Long.class);
    }

    @Override
    public boolean tryLock(long timeoutSec) {
        String threadId = ID_PREFIX + Thread.currentThread().getId();
        Boolean success = stringRedisTemplate.opsForValue()
                .setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(success);
    }

    @Override
    public void unlock() {
        // 原子执行"判断 + 删除"：KEYS[1] = 锁的 key，ARGV[1] = 当前线程标示
        stringRedisTemplate.execute(
                UNLOCK_SCRIPT,
                Collections.singletonList(KEY_PREFIX + name),
                ID_PREFIX + Thread.currentThread().getId());
    }
}
```

**参数映射**（execute 的三个参数怎么进脚本）：

| Java 侧 | 脚本侧 | 内容 |
|---|---|---|
| 第 2 参 `Collections.singletonList(...)` | `KEYS[1]` | 锁的 key：`lock:order:userId` |
| 第 3 参（可变参数） | `ARGV[1]` | 线程标识：`uuid-threadId` |

**三个易错点**：

1. **`DefaultRedisScript` 声明成 `static final` + 静态块加载**：脚本只需解析一次。首次执行时 Spring 底层发 `EVAL`，Redis 会缓存脚本的 **SHA1 摘要**，之后自动走 `EVALSHA` 只传摘要不传全文——这也是 key/参数必须外置的原因之一（脚本本体要固定才能复用摘要）。
2. **`setResultType(Long.class)` 别漏**：不设置的话 Lua 返回值反序列化不出来（`del` 返回 1/0、失败分支返回 0，都按 Long 接）。
3. **第一个参数是 `Collections.singletonList` 不是 `Arrays.asList`**：`execute` 的签名要求 `List<T>`，singletonList 语义更准（就一个 key）。

**温馨小贴士：返回值别浪费**——当前代码忽略了脚本的返回值。返回 0 意味着"发生了本不该发生的误判场景"（我的锁还没删就换了主人），生产上值得记一条 warn 日志甚至报警，这是排查锁异常的重要信号。

### 6.4 直接回答：Lua 解决了什么、没解决什么

**✅ 解决了**：
- **「判断锁标识 + 删除锁」多条命令组合的原子性**——误删问题的最后一块拼图补上了。从此"判断通过后锁被换主人再误删"在物理上不可能发生，因为判断和删除之间不存在可插入的间隙。
- 顺带解决：**条件逻辑**。`if` 分支是 Lua 语言能力，MULTI 给不了。

**❌ 没解决（Redisson 的存在理由，05 篇的主线）**：

| 遗留问题 | 场景 | Redisson 的解法 |
|---|---|---|
| 锁不可自动续期 | 业务执行超过 TTL，锁提前"丢"（现在删不错别人的了，但锁还是会过期，互斥窗口失守） | watchdog 看门狗自动续期 |
| 不可重入 | 同一线程还没释放又想再次获取（方法递归/多层调用），会失败 | hash 结构 + 重入计数 |
| 主从切换锁丢失 | 主节点加锁成功，还没同步到从节点就宕机，从升级为主后锁凭空消失 | RedLock（争议大）/ 多节点 |

**❌ 另一个精确认识：Lua 的原子性 ≠ 数据库事务**：
- 没有**回滚**：脚本中途报错，已执行完的命令不撤销（所以脚本要短小、逻辑简单）；
- 没有**隔离级别**概念：它不是"隔离出一份快照让人慢慢操作"，而是**独占执行**——整个 Redis 在脚本执行期间被这一条"命令"占用；
- 所以说 Lua 是"打包原子"，不是"事务"。这也是为什么脚本里禁止写耗时循环——**脚本执行期间整个 Redis 是阻塞的**。

## 七、秒杀接入（`VoucherOrderServiceImpl` 当前真实版）

```java
@Override
public Result seckillVoucher(Long voucherId) {
    //1.查券 2.判开始 3.判结束 4.判库存（同 03 篇）
    Long userId = UserHolder.getUser().getId();

    SimpleRedisLock lock = new SimpleRedisLock("order:" + userId, stringRedisTemplate);
    boolean isLock = lock.tryLock(1200);
    if (!isLock) {
        return Result.fail("不允许重复下单");   // 同一用户并发第二单直接拒绝，不等待
    }
    try {
        IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
        return proxy.createVoucherOrder(voucherId);
    } finally {
        lock.unlock();
    }
}
```

**对照 03 篇的两个变化**：
1. `synchronized` 用户锁 → 分布式锁（集群可用）；`intern()` 那套不用了。
2. **事务边界收紧回内层**：`seckillVoucher` **不加** `@Transactional`，事务只在 `createVoucherOrder`——锁的范围必须 ≥ 事务的范围（03 篇优化三的原则在 Redis 锁上同样成立，详见踩坑表 #2）。
3. `tryLock(1200)`：TTL 1200s 是业务最长执行时间的兜底估值——**宁长勿短**（短了误删风险大，长了宕机后其他请求多等一会儿，正常路径锁都在 finally 及时释放，TTL 只是保险丝）。

## 九、八股结合点

1. **Redis 单线程与原子性的精确表述**：单条命令原子（INCR 天然并发安全）；**多条命令的组合不原子**（中间可插入其他客户端命令）；Lua 把多条命令打包成一条执行 → 组合原子。RedisIdWorker 的 increment、本篇的 unlock.lua，是同一原理的两处应用。
2. **为什么不用 Redis 事务（MULTI/EXEC）**：MULTI 只是打包排队，命令入队时必须完全确定，**无法表达"后一条依赖前一条结果"的分支逻辑**；Lua 有变量、有 if，能写条件判断。
3. **EVAL 与 EVALSHA**：首次 EVAL 全文 + 缓存 SHA1；后续 EVALSHA 只传摘要。Spring `DefaultRedisScript` 自动处理。分布式锁场景 key/参数外置 + 脚本固定正是为了配合摘要缓存。
4. **分布式锁三要素**：互斥（SETNX）/ 防死锁（TTL）/ 安全释放（标识校验）——标准答案框架，演进线正好逐条覆盖。
5. **Redisson 对比**（学完 05 篇后回头填）：watchdog 续期默认 30s、每 10s 续一次；可重入用 hash（field=线程标识，value=重入计数）；RedLock 争议（Martin Kleppmann vs antirez 论战）。
6. **finally 释放资源**：与 JDBC 连接关闭、线程池 shutdown 同一习惯。

## 十、面试题库

### 🔥 必背五题

1. **你项目里的分布式锁怎么实现的？** SETNX 抢锁（setIfAbsent 一条命令带 TTL，防"setnx+expire 两步间宕机死锁"）+ 锁值存 UUID-threadId 线程标识 + Lua 脚本原子释放。三要素逐条对应：互斥/防死锁/安全释放。
2. **为什么要线程标识？误删怎么发生的？** 线程1业务阻塞（FULL GC）超过 TTL → 锁自动过期 → 线程2拿到新锁 → 线程1醒来 finally 直接 delete 就删了别人的锁 → 线程3又进来，互斥失守。标识让"释放前先确认是我的"成为可能。
3. **为什么要用 Lua 脚本？它怎么保证原子性？** 判断标识和删除是两条命令，中间隔网络往返，线程1判断通过后阻塞、锁过期被线程2抢走，线程1醒来照样误删——equals 校验保护不了判断之后的未来。Redis 内置 Lua 解释器，**整段脚本作为一条命令执行，执行期间单线程不插入其他命令** → 判断+删除不可分割。MULTI/EXEC 不行是因为命令入队时就确定了，写不了 if 分支。
4. **Lua 的原子性和数据库事务一样吗？** 不一样：无回滚（中途出错已执行的不撤销）、无隔离级别（是独占执行不是快照隔离），且执行期间阻塞整个 Redis，所以脚本必须短小。它是"打包原子"，不是"事务"。
5. **你这把锁还有哪些问题？** 三条：不可自动续期（业务超时锁先丢）、不可重入、主从切换锁丢失（异步复制+宕机切换）→ 所以生产用 Redisson（watchdog + hash 可重入），这也是我下一步的改造（05 篇）。

### ⚡ 追问链

- 误删 →"锁过期了业务还没执行完怎么办？"（无解于手写版 → Redisson watchdog）
- Lua →"脚本执行期间 Redis 阻塞，脚本写太大会怎样？"（整个 Redis 卡死，所以脚本必须短；耗时逻辑别塞脚本）
- Lua →"Redis Cluster 下 Lua 有什么限制？"（脚本只能访问同一个 slot 的 key → hash tag）
- tryLock →"拿不到锁为什么直接失败而不是等待？"（秒杀语义：重复下单立即拒绝比排队体验好；可重入锁才谈"等待+重试"）
- 集群 →"TTL 设多长合适？"（业务最长执行时间，宁长勿短；finally 保证正常路径及时释放，TTL 只是宕机保险丝）
