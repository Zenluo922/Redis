## 〇、模块全景与全链路时序

### 0.1 一条演进线（面试先讲动机，再讲实现）

```
V1：Session 实现（单机可用）
    发验证码(存 session) → 登录(用户存 session) → Cookie 带回 JSESSIONID → 拦截器查 session
         ↓ 集群下每台 Tomcat 各有各的 session，不共享 → 问题
V2：Redis 实现（前后端分离 + 集群可用）★ 当前版本
    验证码存 Redis(2min 绝对过期) → 登录发随机 token → 用户 Hash 存 Redis(30min 滑动续期)
    → 前端存 token，每次请求放 header → 拦截器链查 Redis → ThreadLocal → 业务随手取
```

**一句话总结**：session 方案在集群下每台服务器各自为政；把"登录态"从服务器内存搬到共享的 Redis，用无状态 token 做钥匙，用 key 的 TTL 做有效期管理。

### 0.2 全链路时序（对着本项目跑一遍）

| 步骤 | 发生了什么 | 代码位置 |
|---|---|---|
| 1 | 浏览器（nginx 前端 ：8080）点"发送验证码" → `POST /user/code?phone=xxx` | `UserController.sendCode`，参数用 `@RequestParam` |
| 2 | 后端（Boot :8081）校验手机号 → 生成 6 位码 → 存 Redis `login:code:{phone}`，TTL 2min → `log.debug` 模拟发短信 | `UserServiceImpl.sendCode` |
| 3 | 用户填码点登录 → `POST /user/login`，JSON body `{phone, code}` | `UserController.login`，参数用 `@RequestBody` |
| 4 | 校验验证码 → 按手机号查用户（不存在则注册）→ 生成 token → UserDTO 转 Hash 存 Redis `login:token:{token}`，TTL 30min → `Result.ok(token)` | `UserServiceImpl.login` |
| 5 | 前端把 token 存进 sessionStorage（黑马前端写死的逻辑），之后**每个请求**的请求头带 `authorization: {token}` | 前端 nginx 代码（约定） |
| 6 | 每个请求进来：`RefreshTokenInterceptor`(order 0) 查 Redis → 装配 ThreadLocal → 刷新 TTL；`LoginInterceptor`(order 1) 只查 ThreadLocal 做门槛 | `config/MvcConfig` 注册 |
| 7 | Controller 里 `UserHolder.getUser()` 随手拿用户（如 `GET /user/me`） | `UserController.me` |
| 8 | 响应结束，`afterCompletion` **逆序**执行，`UserHolder.removeUser()` 清理 ThreadLocal | `RefreshTokenInterceptor.afterCompletion` |

> 统一返回结构 `Result`：`{success: Boolean, errorMsg: String, data: Object}`，静态方法 `ok()/ok(data)/fail(msg)`——全项目接口一个形状。

## 二、V1：基于 Session 实现（演进基线，代码已不在项目中）

### 2.1 V1 是什么样

- 验证码：`session.setAttribute("code", code)`；登录：`session.setAttribute("user", UserDTO)`
- 拦截器：`session.getAttribute("user")`，null → 401；否则 `UserHolder.saveUser(userDTO)`
- 凭证：浏览器 Cookie 自动带 `JSESSIONID`，前端无感知

### 2.2 V1 的两个设计遗产（V2 继承）

- **UserDTO 脱敏**：session/缓存里只放前端需要的最小字段
- **ThreadLocal 保存当前用户**：业务代码不层层传参

### 2.3 V1 为什么必须升级（面试必答）

Tomcat 的 session 存在**本机内存**。集群下负载均衡把请求分发到不同节点：第一次登录在 A 机，第二次请求落在 B 机 → B 机没有 session → 被判未登录。三种解法：

| 方案 | 做法 | 缺点 |
|---|---|---|
| session 复制 | 节点间同步 session | 拷贝开销大、占内存、有延迟 |
| 粘性路由 | 同一用户固定打同一节点 | 破坏负载均衡；节点挂了 session 全丢 |
| **共享存储 Redis ✅** | 登录态集中存 Redis | 多一次网络 IO，但内存读写快 + key 可设 TTL |

Redis 的两个天然契合点：**KV 结构**正好表达 token→用户；**TTL 机制**天然管理有效期。

- **参数注解是前后端约定**：发验证码前端把手机号拼在 URL 上 → `@RequestParam`；登录前端发 JSON body → `@RequestBody`（配 LoginFormDTO 反序列化）。接口报 400/拿不到值时先查这个。

- **`logout` 还是 TODO**（课程留白）：正确的实现 = Redis `DEL login:token:{token}` + `UserHolder.removeUser()` + 前端清 storage。见第七节改造点。
- **两个方法的 `HttpSession session` 参数是迁移残留**：V2 里根本没用 session，签名可以删掉（课程为了少改没删，你知道就行）。

### 3.2 发送验证码：UserServiceImpl.sendCode

```java
@Override
public Result sendCode(String phone, HttpSession session) {
    //1.校验手机号
    if (RegexUtils.isPhoneInvalid(phone)) {
        //2.如果不符合，返回错误信息
        return Result.fail("手机号格式错误！");
    }
    //3.符合，生成验证码
    String code = RandomUtil.randomNumbers(6);
    //4.保存验证码到redis
    stringRedisTemplate.opsForValue()
        .set(LOGIN_CODE_KEY + phone, code, LOGIN_CODE_TTL, TimeUnit.MINUTES);
    //5.发送验证码
    log.debug("发送短信验证码成功，验证码：{}", code);
    return Result.ok();
}
```

【逐段拆解】
- **第 1 段·先校验再干活**：`RegexUtils.isPhoneInvalid` 内部是 `blank → 无效`，再 `!str.matches(正则)`。脏参数在入口挡掉，后面代码不用再防 null。
- **第 3 段·hutool 造码**：`RandomUtil.randomNumbers(6)` 直接生成 6 位数字字符串。
- **第 4 段·`set` 的四参重载是重点**：`set(key, value, timeout, unit)` = **写入的同时设 TTL**，原子一步。存 `login:code:{phone}`，2 分钟——为什么 key 用手机号？因为登录时用户提交的就是"手机号+验证码"，用手机号反查才能对上（**业务字段做 key 的对应关系**）。为什么 String 结构？单值场景，String 最合适——**单值用 String，对象用 Hash**。
- **第 5 段·`log.debug` 模拟发短信**：真实项目接短信服务商 SDK；debug 级别保证生产日志里不泄露验证码。

### 3.3 登录：UserServiceImpl.login（核心方法）

```java
@Override
public Result login(LoginFormDTO loginForm, HttpSession session) {
    //1.校验手机号
    String phone = loginForm.getPhone();
    if (RegexUtils.isPhoneInvalid(phone)) {
        return Result.fail("手机号格式错误！");
    }

    //3.从redis获取验证码并校验
    Object cacheCode = stringRedisTemplate.opsForValue().get(LOGIN_CODE_KEY + phone);
    String code = loginForm.getCode();
    if (cacheCode == null || !cacheCode.toString().equals(code)) {
        return Result.fail("验证码错误");
    }

    //4.一致，根据手机号查询用户
    User user = query().eq("phone", phone).one();

    //5.判断用户是否存在
    if (user == null) {
        //6.不存在，创建新用户并保存（登录注册合一）
        user = createUserWithPhone(phone);
    }

    //7.存在，保存用户信息到redis当中
    //7.1随机生成token作为登录令牌
    String token = UUID.randomUUID().toString(true);
    //7.2将User对象转为Hash存储
    UserDTO userDTO = BeanUtil.copyProperties(user, UserDTO.class);
    Map<String, Object> userMap = BeanUtil.beanToMap(userDTO, new HashMap<>(),
            CopyOptions.create().setIgnoreNullValue(true).
                    setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString()));
    //7.3存储
    String tokenKey = LOGIN_USER_KEY + token;
    stringRedisTemplate.opsForHash().putAll(tokenKey, userMap);
    //7.4设置token有效期
    stringRedisTemplate.expire(tokenKey, LOGIN_USER_TTL, TimeUnit.MINUTES);

    //8.返回token
    return Result.ok(token);
}
```

【逐段拆解】

**验证码校验段（坑最多的一行）**：
- `cacheCode == null || !cacheCode.toString().equals(code)`——**先判 null 再 equals**，顺序不能反。null 的两种来源：验证码过期被 Redis 删了；根本没发过码。`||` 短路保证不会对 null 调 `.toString()` 抛 NPE。
- 一个隐藏安全问题：**校验通过后验证码没有删除**，同一个码 2 分钟内可以反复登录 → 改造点见第七节。
- 小冗余：`cacheCode` 声明成 `Object`（`get` 实际返回 String），照抄课程 so 无妨，声明为 String 更清晰。

**查用户段**：
- `query().eq("phone", phone).one()` 是 MyBatis-Plus 条件构造器 = `SELECT * FROM tb_user WHERE phone = ? LIMIT 1`。phone 在表上有唯一性，`one()` 安全。

**注册登录合一**：手机验证码模式下"登录即注册"——新手机号查不到用户就 `createUserWithPhone` 建一个再走登录。**不存在独立注册接口**，这是验证码登录的产品特点，面试描述流程时要点出来。

**发 token 段**：
- `UUID.randomUUID().toString(true)`：122 位随机熵 + `true` 去掉横线。**绝不能用手机号/自增 id 当 token**——可被枚举伪造（见面试 Q2）。
- `copyProperties(user, UserDTO.class)`：先脱敏（见 3.5）。
- `tokenKey = LOGIN_USER_KEY + token` → `login:token:{token}`：**前缀 + 随机 token 的两段式 key**，业务前缀归类，token 保证唯一。
- `putAll` + `expire` 两行都引用**同一个 `tokenKey` 变量**——这不是随手写的：曾经少拼了前缀直接导致登录后永远 401（踩坑记录 #2），教训就是 **key 拼装收敛到一个变量**。

### 3.4 ★ beanToMap 带 CopyOptions：两个运行时炸弹（本项目真踩过）

裸写 `BeanUtil.beanToMap(userDTO)` 编译能过，运行时两个炸弹：

**炸弹① null 字段 → putAll 抛异常**
- `UserDTO.icon` 可能为 null（新用户没头像）
- **Redis Hash 的 field value 不允许是 null**，`opsForHash().putAll()` 碰到 null entry 直接异常
- 解：`setIgnoreNullValue(true)` 跳过 null 字段——不存即不存在，取回来自然是 null，语义无损

**炸弹② Long 字段 → ClassCastException**
- `id` 是 `Long`，而 `StringRedisTemplate` 的 key/value/hashValue 序列化器全是 `StringRedisSerializer`，只认 String
- 往 Hash 塞 Long 的瞬间：`java.lang.ClassCastException: java.lang.Long cannot be cast to java.lang.String`
- 解：`setFieldValueEditor((k, v) -> v.toString())` 给每个字段值统一套 toString

**读法**：`CopyOptions.create()` 是 hutool 的"拷贝选项"配置对象，链式挂两个规则；`beanToMap(userDTO, new HashMap<>(), options)` = 把 userDTO 的字段按规则拷进新 Map。

**存取闭环（为什么全转 String 不丢数据）**：拦截器取回时 `BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false)` 把 Map 转回对象，hutool 自动把 `"1"` 转回 `Long id = 1`。

> 面试一句话版："StringRedisTemplate 要求 Hash value 是字符串、Redis Hash 不允许 null 值，所以用 hutool 的 CopyOptions 过滤 null、统一 toString；取的时候 fillBeanWithMap 自动转回对象类型。"

### 3.7 续命层：RefreshTokenInterceptor（order 0，拦 /**）

```java
public class RefreshTokenInterceptor implements HandlerInterceptor {

    private StringRedisTemplate stringRedisTemplate;

    public RefreshTokenInterceptor(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        //1.获取请求头中的token
        String token = request.getHeader("authorization");
        if (StrUtil.isBlank(token)) {
            //没带token：放行，由LoginInterceptor决定是否拦截
            return true;
        }
        //2.基于TOKEN获取redis中的用户
        String key = RedisConstants.LOGIN_USER_KEY + token;
        Map<Object, Object> userMap = stringRedisTemplate.opsForHash().entries(key);
        //3.判断用户是否存在
        if (userMap.isEmpty()) {
            //4.不存在（token无效）：放行，由LoginInterceptor决定是否拦截
            return true;
        }
        //5.将查询到的Hash数据转为UserDTO对象
        UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);
        //6.存在，保存用户信息到ThreadLocal
        UserHolder.saveUser(userDTO);
        //7.刷新token有效期
        stringRedisTemplate.expire(key, RedisConstants.LOGIN_USER_TTL, TimeUnit.MINUTES);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        UserHolder.removeUser();
    }
}
```

【逐段拆解】
- **构造器注入（本类最特殊的设计）**：拦截器是 `new` 出来的，**不是 Spring Bean**，`@Resource` 注进来只会是 null。所以让 `MvcConfig`（它是 Bean）注入 template，再构造器"递"进来。这个"递"字就是构造器传递模式的全部。
- **两处 `return true` 是本类的灵魂**（踩坑记录 #6）：它拦的是 `/**`，**包括 `/user/code`、`/shop/**` 这些免登录路径**。没 token 就 401 的话，用户连验证码都申请不了，整站废掉。它的职责只有"续命"，**401 只能由 LoginInterceptor 给**。
- **`entries(key)`** = `HGETALL`，一次拿整个 Hash。empty 判定覆盖三种情况：token 过期被删、token 是伪造的、Redis 里压根没有——统一按"没登录"放行。
- **`fillBeanWithMap(userMap, new UserDTO(), false)`**：Map→Bean，第三参 `ignoreError=false` 表示类型转换失败直接抛异常（fail-fast，不吞错误）。
- **第 7 步 `expire` 就是"30 分钟滑动续期"的全部实现**：只要用户还在活跃（访问任何页面），TTL 就被重置回 30 分钟；停止访问 30 分钟后 key 过期 → 下次请求 `entries` 拿到空 → 未登录。**登录态的生命周期管理 = 一行 expire**。
- **`afterCompletion` 里 `removeUser()`**：为什么放这里而不是 Controller——见 3.9 的执行顺序分析。

### 3.8 门槛层：LoginInterceptor（order 1）

```java
public class LoginInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        //1.判断是否需要拦截（ThreadLocal中是否有用户）
        if (UserHolder.getUser() == null) {
            //2.没有，需要拦截，设置状态码
            response.setStatus(401);
            //3.拦截
            return false;
        }
        //4.有用户，放行
        return true;
    }
}
```

【拆解】
- 它**不碰 Redis、不碰请求头**——只看 ThreadLocal 里有没有前一层装好的用户。拆分后它连构造器都没有（踩坑记录 #4 的反向结果）。
- `401 Unauthorized` + `return false` 缺一不可：只 setStatus 不 return false，等于贴了张罚单还是放行（踩坑记录 #5）。前端 axios 拦截器看到 401 会跳登录页。
- 放行路径之外的一切都要过这道门：`/user/me`、`/voucher-order/**`、`/blog/**`（除 hot）等。

### 3.9 注册与顺序：MvcConfig

```java
@Configuration
public class MvcConfig implements WebMvcConfigurer {

    @Resource
    private StringRedisTemplate stringRedisTemplate;   // MvcConfig 是 Bean，能注入

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginInterceptor()).
                excludePathPatterns(
                        "/shop/**",        // 商铺浏览/详情：游客可看
                        "/voucher/**",     // 优惠券列表：游客可看
                        "/shop-type/**",   // 首页商铺类型：游客可看
                        "/upload/**",      // 静态图片
                        "/blog/hot",       // 热门探店笔记：游客可看
                        "/user/code",      // 发验证码：登录前必须可用
                        "/user/login").order(1);   // 登录本身
        registry.addInterceptor(new RefreshTokenInterceptor(stringRedisTemplate))
                .addPathPatterns("/**").order(0);   // 构造器"递"进去
    }
}
```

【拆解】
- **⚠️ 细微但致命的一点**：`excludePathPatterns` 只对 **LoginInterceptor 自己**生效。RefreshTokenInterceptor 配的是 `/**`，**放行路径它照样拦**——所以它必须"查不到也放行"（3.7 的 return true），两个设计互为因果。
- **执行顺序**：`preHandle` 按 order 升序（0→1），`postHandle`/`afterCompletion` 按**逆序**（1→0）：

```
请求 → Refresh.preHandle(0) → Login.preHandle(1) → Controller → 响应
退出 → Login.afterCompletion(1) → Refresh.afterCompletion(0)
```

- **为什么 removeUser 放在 Refresh（order 0）的 afterCompletion？三个理由**：
  1. afterCompletion 只对 **preHandle 已执行且返回 true 的拦截器**逆序调用。Login 可能 `return false`（拦截），那时它自己的 afterCompletion 不会被调，但 Refresh 的会（它 preHandle 恒 true）→ **放最外层 = 必然执行**；
  2. Refresh 的 preHandle 对任何请求都返回 true → 它的 afterCompletion **每个请求都走**，清理无一遗漏；
  3. Tomcat 线程池线程复用，不清就串号（见第五节）。
- **排除路径的设计原则**：游客可浏览的内容 + 登录流程本身放行；一切"写操作"和"个人数据"（`/user/me`、`/voucher-order/**`、`/blog` 的发布）受保护。

### 3.10 常量与工具：RedisConstants / RegexUtils

**登录相关 4 个常量（`RedisConstants`）**：

| 常量 | 值 | 用在哪 |
|---|---|---|
| `LOGIN_CODE_KEY` | `"login:code:"` | 验证码 key 前缀（+手机号） |
| `LOGIN_CODE_TTL` | `2L` | 验证码 2 分钟，绝对过期 |
| `LOGIN_USER_KEY` | `"login:token:"` | 登录态 key 前缀（+token） |
| `LOGIN_USER_TTL` | `30L` | 登录态 30 分钟，**滑动续期** |

> key 命名规范 `业务:层级:标识`——RESP 里一眼归类，`KEYS login:*` 按业务扫描。两种 TTL 语义不同：**验证码是绝对过期**（到点即废），**登录态是滑动续期**（每次请求重置 30 分钟，持续活跃永不过期）。

**`RegexUtils.mismatch`**：先 `blank → 无效`（防 null/空串），再 `!matches(regex)`。工具类的 defensive 写法值得学。

## 四、★ 本模块踩坑记录（复盘用，面试讲"我踩过的坑"素材）

| # | 现象 | 原因 | 修复 | 教训 |
|---|---|---|---|---|
| 1 | `UserHolder.saveUser((User) user)` 编译爆红 | `saveUser` 参数是 `UserDTO`，链路数据形状是 DTO 不是实体 | 强转 UserDTO，并把存储侧统一为 UserDTO | ThreadLocal 泛型决定了整条链路的数据形状，存储/拦截/业务三端必须一致 |
| 2 | 登录成功后前端永远 401 | `putAll(token, userMap)` 用了裸 token，少拼 `login:token:` 前缀；而拦截器查的是带前缀的 key | set 和 expire 统一用 `tokenKey` 变量 | key 拼装收敛到一个变量，杜绝两处手拼不一致 |
| 3 | `beanToMap` 不带参数版一跑就炸 | ①icon=null：Redis Hash value 不允许 null；②id 是 Long：StringRedisTemplate 序列化器只认 String → CCE | `setIgnoreNullValue(true)` + `setFieldValueEditor(toString)` | StringRedisTemplate 的"全 String 世界"边界要清楚 |
| 4 | 拆分拦截器过渡期编译错：`new LoginInterceptor()` 不匹配构造器 | LoginInterceptor 暂时还留着带 StringRedisTemplate 的构造器 | 拆分完成后 LoginInterceptor 不再需要 Redis，删掉构造器 | 中间态报错先看清"谁需要谁"再动手 |
| 5 | preHandle 写成 `handler instanceof HandlerMethod` 且缺 `return false` | 判断对象错位（那只判断"目标是不是控制器方法"，几乎所有请求都 true）；且 setStatus 后没 return false，照样放行 | 正确逻辑：`UserHolder.getUser() == null → 401 → false` | 拦截器"拦截"的唯一含义是 return false |
| 6 | RefreshTokenInterceptor 查不到用户给了 401 | 职责错位：它拦 `/**`，没 token 就 401 = 免登录路径全废，连验证码都申请不了 | 两处改 `return true` 放行，401 只留给 LoginInterceptor | **续命层永远放行，准入层才给 401**——"直觉合理但架构错误"的典型 |
| 7 | `LOGIN_USER_TTL = 36000` | 手误/误改，36000 分钟 = 25 天，等于永不过期 | 改回课程原版 30L | TTL 是登录态安全的生命线，滑动续期 30min 是设计好的安全窗口 |

## 五、ThreadLocal 深入（八股结合点）

### 5.1 UserHolder 与结构

```java
public class UserHolder {
    private static final ThreadLocal<UserDTO> tl = new ThreadLocal<>();
    public static void saveUser(UserDTO user) { tl.set(user); }
    public static UserDTO getUser() { return tl.get(); }
    public static void removeUser() { tl.remove(); }
}
```

```
Thread 对象
 └── ThreadLocalMap（每个线程一个）
      └── Entry[]
           └── Entry：key = ThreadLocal 实例（弱引用），value = UserDTO（强引用）
```

`saveUser` 的值存在**当前执行线程**自己的 Map 里——线程隔离，天然并发安全。为什么不用参数层层传：Controller→Service→Mapper 全链加参数污染签名；ThreadLocal 是"请求作用域上下文"，业务与横切关注点解耦。

### 5.2 内存泄漏链路（面试标准讲解）

1. Entry 的 **key 是弱引用**：外部代码不再引用这个 ThreadLocal 实例时，key 被 GC → Entry 变成 `key=null` 的陈旧条目
2. **value 是强引用**：`Thread → ThreadLocalMap → Entry → value`，只要线程活着 value 就回收不掉
3. Tomcat 线程池**线程长期存活** → value 永远挂着 → 泄漏

**为什么 key 设计成弱引用**：反向想——若 key 是强引用，ThreadLocal 实例外部没人用了也回收不掉，泄漏更彻底。弱引用至少保证 key 可回收，且 get/set 探测到 `key=null` 的条目会顺手清 value（探测式清理）。**但这是"下次用到才清"，不可靠，规范是必须手动 remove。**

### 5.3 比泄漏更狠：脏数据（本项目必须 remove 的真正原因）

线程复用：线程 T 处理完用户 A 的请求没 remove，接着处理用户 B 的请求 → B 的链路上若没人 saveUser，`UserHolder.getUser()` 拿到 **A 的用户** → 数据串号，业务事故级别。这就是 `removeUser()` 必须放在 afterCompletion（且是最外层那个）的根源。

## 六、面试题库

> 每题先背"一句话版"，再展开要点。标准：不看答案口述 2 分钟。

### 🔥 必背五题

**Q1：为什么登录用 Redis 而不用 session？**
- 一句话版："session 存在单机内存，集群下不共享；把登录态搬进 Redis，任何节点都能校验，且 key 的 TTL 天然管理有效期。"
- 展开：集群 session 问题 → 三方案对比（复制/粘性/共享存储）→ Redis 契合点（内存快、KV、TTL）→ 主动讲滑动续期。

**Q2：为什么用 token？token 怎么设计？**
- 一句话版："前后端分离和 App 没有 Cookie，改用服务端签发的随机 UUID 当 token，前端存本地，每次请求放 authorization 头。"
- 展开：session 依赖 Cookie → token 跨端；UUID 122 位随机熵不可枚举（反例：手机号可遍历伪造）；token 只是无意义钥匙，数据在 Redis，**服务端 DEL key 即可强制下线**。

**Q3：用户信息为什么用 Hash 存，不用 String 存 JSON？**
- 一句话版："Hash 支持字段级读写，改一个字段不用整体序列化覆盖，小对象内存更省；只做整体读写的话 String 也行——单值用 String，对象用 Hash。"
- 展开：对比（字段级 HSET/HGET vs 整体覆盖）；主动提 SpringSession 就是 String 存 JSON，显得懂权衡；本项目取回用 fillBeanWithMap 自动转回类型。

**Q4：拦截器为什么拆成两个？**
- 一句话版："刷新 token 要覆盖所有请求（放行页面也得续期），登录校验只管受保护路径——两个职责的拦截范围不同，按 order 拆两层。"
- 展开：单拦截器的 bug（逛放行页不刷 token，活跃用户照样被踢）→ 分工：Refresh(order 0, /**) 续命 + 装配 ThreadLocal 且**查不到也放行**；Login(order 1) 只查 ThreadLocal 给 401 → removeUser 放最外层 afterCompletion 的原因（逆序执行 + return false 不触发自己的 afterCompletion）。

**Q5：ThreadLocal 是什么？为什么内存泄漏？怎么解决？**
- 一句话版："每个线程自带 ThreadLocalMap，key 弱引用、value 强引用；key 被 GC 后 value 被线程强引用链挂住，线程池线程不死就回收不掉；规范是 afterCompletion 里手动 remove。"
- 展开：结构 → 泄漏链 → 弱引用设计动机 → **Tomcat 线程复用的脏数据问题（比泄漏更严重的业务事故）** → 本项目 removeUser 放 order 0 的 afterCompletion，三个理由。

### ⚡ 追问链

**Q6：Redis 挂了用户全下线怎么办？**
主从+哨兵（或 Cluster）保高可用；RDB/AOF 持久化，重启可恢复；极端情况降级：校验退回数据库查用户（性能差但可用）。体现单点风险意识即可。

**Q7：token 被窃取怎么办？**
HTTPS 防传输窃听；TTL 短 + 滑动续期缩小窗口；服务端直接 DEL key 强制下线——token+Redis 相比 JWT 的核心优势（可控性）。

**Q8：为什么不用 JWT？**
JWT 无状态：签名自校验、不查存储、天然分布式；但**签发后无法作废**（强制下线只能黑名单=又回到有状态）、payload 每请求携带体积大、改信息要重签。本项目需要服务端控制登录态（强制下线、失效管理）且 Redis 本就在架构里。答"两种都懂，按场景选"最加分。

**Q9：验证码接口会不会被刷？怎么防？**
课程没做（诚实说），方案知道：同手机号 60s 间隔 + 每日上限（INCR+EXPIRE）、IP 限流、图形/行为验证码前置、**验证码一次性（校验成功即 DEL）**、TTL 短。也是项目改造点素材。

**Q10：Spring Session 了解吗？和你的方案比？**
SpringSession 把 HttpSession 透明替换为 Redis（Cookie 里的 SESSIONID 指向 Redis），业务无感；缺点：仍绑 Cookie、App 不友好、黑盒。手写 token：跨端、可控、原理透明。学习项目选手写方案更能讲清原理。
