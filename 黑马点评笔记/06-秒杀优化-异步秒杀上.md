## 〇、全景：异步化的核心思想

```
V5 同步版（05 篇成果，Redisson 锁）：
  请求线程包办全部：查券 → 判时间 → 判库存 → Redisson 抢锁 → count 一人一单
   → 乐观锁扣库存 → 插订单（事务）→ 返回
      ↓ 痛点一：请求线程从进到出几十~几百ms，Tomcat 线程池有限（默认200）
         → 秒杀高峰 1000 个请求排队 → 超时/拒绝
      ↓ 痛点二：写库是行锁串行的，数据库每秒只能消化几单，这才是最终瓶颈
V6 异步版（当前）★：
  请求线程只干一件快事：Lua 一条命令判断资格（库存+一人一单+预扣库存，纯Redis内存操作，微秒级）
   → 资格通过 → 生成订单对象 → 塞进内存阻塞队列 → 立即返回订单号
  后台单线程消费者：从队列取单 → Redisson 锁 → 事务写库（慢就慢吧，反正用户已经走了）
V7（下一站 ch7）：阻塞队列 → Redis Stream 消息队列（本篇第七节讲为什么必须换）
```

**一句话总结**：把"**能不能买**"（判断，快）和"**把单写进库**"（动作，慢）拆开——判断用 Lua 在 Redis 里一次做完，动作丢给后台线程慢慢做。**白话比喻（奶茶店）**：以前是一个店员从点单、做奶茶到打包全程包办，队伍越排越长；现在点单员只管收钱打小票（秒杀接口，瞬间完事），小票夹到出餐口（阻塞队列），后厨师傅（消费者线程）按小票慢慢做——客人拿到小票就走了，不用站在柜台前等奶茶。

**风险先摆明**（后面第七节展开）：客人拿了小票但奶茶没做出来就打烊了怎么办？——所以有界队列的容量、宕机丢单、集群队列不共享，是阻塞队列版的三宗罪，也是引入消息队列的全部动机。

## 〇.5、概念垫底：异步 & 阻塞队列（没听懂先读这节，5 分钟）

> 本节不涉及秒杀，把两个词从零讲透。看懂这节，正文第四节的代码只是"往这张图里填业务"。

### A. 异步：核心就一个问题——"你等不等"

#### A.1 生活判断题

去大厅办证：
- **同步**：把材料递给窗口，**站在窗口前**等审核、盖章、归档全部做完，拿到证才离开。这几小时你哪儿也去不了。
- **异步**：窗口收下材料，给你一张**回执单**（受理凭证），"回家等通知"。你立刻走了，办事员慢慢办，办完打电话通知你。

两种方式**事情都被办了**，唯一区别：**你在不在原地等**。

#### A.2 代码里的判定标准

| | 同步调用 | 异步调用 |
|---|---|---|
| 形式 | `Result r = doSomething()`，返回 = 已办完 | `doSomethingAsync()` 扔出去就返回，返回 = 已受理 |
| 拿到的东西 | 最终结果 | 受理凭证（订单号），结果以后再说 |
| 调用期间 | 调用方卡住，啥也干不了 | 调用方立刻解放 |
| 结果在哪 | 就在返回值里 | 以后查 / 被通知（"最终一致"） |

#### A.3 你其实早就用过异步（项目内的证据）

RedisIdWorker 压测代码（03 篇 2.4 节）：

```java
for (int i = 0; i < 300; i++) es.submit(task);   // ← 异步：丢给线程池，主线程不等它跑完
latch.await();                                    // ← 这行才是事后"收结果"的补偿手段
```

`submit` 那一刻主线程根本不知道任务跑没跑——它只是把任务**托付**出去，自己继续循环。这就是异步。对比一个**同步**的例子：`stringRedisTemplate.get(key)`——这行不返回你就走不了下一行，调用方死等结果。

#### A.4 秒杀新旧版对照

旧版（同步）：请求线程从判库存一路等到 insert 提交，几百 ms 才返回——用户全程"站在窗口前"。
新版（异步）：

```
请求线程：Lua 判资格（微秒级）→ 登记订单 → 立刻返回订单号   ← 订单号就是回执单！
后台线程：取单 → 写库（几十ms，随便慢）→ 写完时用户早已离开
```

用户拿订单号查订单表**暂时查不到是正常的**，等后台写完就有了（毫秒级延迟）——这叫**最终一致**。

#### A.5 异步的代价（诚实清单，正文第七节的三宗罪就是第 2 条的展开）

1. **立刻拿不到结果**——所以凭证必须靠谱（订单号真实对应将来的订单）；
2. **活可能丢**——受理了但没办（后台线程死了/服务重启）；
3. **出错处理变难**——同步版能把"库存不足"当场返回；异步版只能受理后在后台失败（日志/补偿）。

### B. 阻塞队列：异步的"交接台"

#### B.1 为什么异步必须有个交接的地方

异步 = 派活的人和干活的人**不同时在场**。派完活人就走了，活放在哪？放变量里两个线程并发读写是灾难；放普通 List 线程不安全（丢元素、并发修改异常）；自己用 wait/notify 手搓等待唤醒，写得出但极易错。**BlockingQueue = 队列 + 线程安全 + 空了等/满了等，三件事官方全做好。**

#### B.2 拆词：队列（人人都懂）+ 阻塞（灵魂，修饰的是"线程"）

队列：FIFO 先进先出，先点的单先做——这半边没难度。
阻塞：**线程被挂起卡住**，两个方向自动生效：

| 方向 | 场景 | 行为 |
|---|---|---|
| 消费者 `take()` | 队列**空** | 线程挂起睡大觉（**不占 CPU**，不是空转！），有元素入队时自动唤醒取走 |
| 生产者 `put()` | 队列**满** | 线程挂起等待，腾出空位时自动唤醒放入 |

**白话：出餐口**。后厨师傅没单可做就靠在出餐口睡；架子放满了，服务员也卡在原地等师傅腾架子。

> **温馨小贴士（接你学过的多线程）**：这套"自动睡/自动醒"底层就是 `wait/notify` 的封装——take 时发现队列空 → 内部 await 挂起；put 进元素 → 内部 signal 唤醒。你学过的原理，被封装进了一行 `take()`，没有任何魔法。

#### B.3 核心方法表（面试也考）

| 方法 | 语义 | 满/空时的行为 |
|---|---|---|
| `put(e)` | 放入 | 满了**阻塞等待** |
| `take()` | 取出 | 空了**阻塞等待** |
| `add(e)` | 放入 | 满了抛 `IllegalStateException`（本项目用它：满=拒绝，宁可失败不无限堆） |
| `poll()` | 取出 | 空了返回 **null**（不等） |
| `offer(e)` | 放入 | 满了返回 **false**（不等） |
| `peek()` | 只看队头不取 | 空返回 null |

三组记法：**阻塞组** put/take、**即时组** add/poll/offer（失败抛异常或返回特殊值，绝不等待）、**偷看组** peek。本项目中生产者用 `add`、消费者用 `take`。

#### B.4 为什么要"有界"（ArrayBlockingQueue 必须传容量）

内存有限。无界队列（如不传容量的 LinkedBlockingQueue）高峰期只进不出 → 内存涨到 OOM，整个服务挂掉——比丢单严重得多。**有界 = 保险丝**：满了生产者被卡住或拒绝，系统"慢下来"而不是"死掉"（这个思想有个名字：**背压 backpressure**，八股延伸词）。

#### B.5 最小可跑 demo（亲眼看"自动睡、自动醒"）

```java
public static void main(String[] args) throws InterruptedException {
    BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);

    // 消费者线程：先启动，此刻队列是空的
    new Thread(() -> {
        try {
            System.out.println("消费者：等着取单……");
            String order = queue.take();            // ← 卡在这睡大觉（队列空）
            System.out.println("消费者：做到订单 " + order);
        } catch (InterruptedException ignored) { }
    }).start();

    Thread.sleep(3000);                             // 主线程故意拖3秒，证明消费者真睡着
    System.out.println("生产者：放入 订单1");
    queue.put("订单1");                              // ← put 一瞬间消费者被唤醒
}
```

运行观察：打印"等着取单"后**卡 3 秒**（期间消费者线程是挂起状态，不耗 CPU），`put` 之后立即打印"做到订单"。全程没写一行 wait/notify——这就是"阻塞"的全部含义。

### C. 两者拼起来（对应本项目代码）

```
异步 = 行为：派完活就走人，不等结果（add 完立刻 return）
阻塞队列 = 载体：两边都够得着的台子，没活自动睡、有活自动醒

seckillVoucher（点单员，请求线程）         VoucherOrderHander（后厨，消费者线程）
  资格通过 → 造订单对象                        while(true) { orderTasks.take() ← 没单就睡
  orderTasks.add(订单) ───→【ArrayBlockingQueue 出餐口】───→   }
  return Result.ok(orderId) ← 用户走了        Redisson 锁 → 事务写库 → unlock
```

- 没有队列：任务没法安全交接（要么退回同步自己写，要么丢给一个"没准备好"的人）；
- 没有异步：队列没意义（你自己等自己写完就是同步）。
**两者是一对：异步是目的，阻塞队列是支撑异步安全交接的手段**。这个组合的正式名字叫**生产者-消费者模式**（面试常考，阻塞队列是它的标准实现载体）。

## 一、同步版为什么撑不住（瓶颈分析，ch6.1）

1. **Tomcat 线程是稀缺资源**：一个请求从进到出**独占一个线程**。同步版单请求耗时 = 查券(查库) + 判时间 + Redisson 锁 + count(查库) + update(行锁) + insert ≈ 几十到几百 ms（有事务和行锁时更长）。
2. **算一笔账**：Tomcat 默认 200 工作线程，单请求平均 100ms → 理论上限 2000 QPS；秒杀开抢瞬间几千 QPS 涌入 → 线程池打满 → 后面的请求在队列里干等 → 前端超时、用户体验崩塌。
3. **数据库是更深的瓶颈**：扣库存是同一行的 update，行锁下天然串行——不管 Tomcat 多能扛，数据库每秒就消化那么几单写。**扩 Tomcat 解决不了写库**。

**优化公式**：吞吐 = 线程数 ÷ 单请求耗时。线程数改不动（成本），就把**单请求耗时打到极致**——请求线程只做内存操作（微秒级），耗时降到原来的 1/1000，同一台 Tomcat 瞬间能接住十倍流量。剩下的慢活交给后台，**后台线程不占 Tomcat 线程池**。

## 二、改造思路 + Redis 数据准备（ch6.2 前半）

### 2.1 判断资格需要什么数据，Redis 里怎么放

资格判断 = 两个问题：**库存还有吗？这个人买过吗？** 两个都要快、都要并发安全 → 放 Redis，用原子命令：

| key | 类型 | 内容 | 用的原子命令 |
|---|---|---|---|
| `seckill:stock:{voucherId}` | String | 该券剩余库存 | `incrby key -1` 原子预扣 |
| `seckill:order:{voucherId}` | Set | 该券所有已下单的 userId | `sismember` 判重 / `sadd` 记录 |

> **为什么库存用 String 不用 Hash**：一个数字，incrby 天然原子，最简单。
> **为什么一人一单用 Set**：sismember 是 O(1) 且天然去重，"这个人在不在这个集合里"一句话的事。

### 2.2 预热：上线时把库存灌进 Redis

Redis 里的库存不会凭空出现，要在秒杀开始前把 DB 的库存**预热**进去（课程手动操作）：

```bash
redis-cli -a 123321 set seckill:stock:10 100      # 测试券 id=10，库存 100
# 测试前清掉一人一单记录（重要！否则上一轮测试的人全被"不能重复下单"拦住）
redis-cli -a 123321 del seckill:order:10
```

生产做法（了解即可）：应用启动钩子 `@PostConstruct` / 管理端后台按钮 / 定时任务同步。⚠️ **每次测试前先 reset 这两个 key**，本项目已经踩过：Redis 里残留 order set，怎么测都是"不能重复下单"。

### 2.3 心里要有数：现在有两份数据了

Redis 库存是"**预售票**"，MySQL 库存是"**座位表**"。Redis 说有票、DB 写入却失败的可能永远存在（预扣成功 → 消费者写库失败）。课程的处理：**消费者里仍然做 count + update 兜底校验**，失败只记日志（Redis 多扣的那一张就多扣了）。真实生产需要补偿机制（回滚 Redis / 对账任务）——课程不深入，面试当"我知道局限在哪"的加分点讲。

## 三、Lua 资格判断脚本逐行精讲（ch6.2 ★ 本篇核心）

### 3.1 完整脚本（`resources/seckill.lua` 当前版）

```lua
-- 1.参数列表
local voucherId = ARGV[1]        -- 优惠券id（从Java传进来）
local userId = ARGV[2]           -- 用户id

-- 2.数据key（注意带冒号，和预热写入的 key 完全一致）
local stockKey = 'seckill:stock:' .. voucherId    -- '..' 是 Lua 的字符串拼接
local orderKey = 'seckill:order:' .. voucherId

-- 3.脚本业务
-- 3.1.库存不足？get 返回的是字符串，tonumber 转成数字再比较
if (tonumber(redis.call('get', stockKey)) <= 0) then
    return 1                      -- 1 = 库存不足
end
-- 3.2.重复下单？sismember 返回 1/0，必须 == 1 判断（Lua 里 0 也是真值！）
if (redis.call('sismember', orderKey, userId) == 1) then
    return 2                      -- 2 = 重复下单
end
-- 3.3.预扣库存（incrby 原子）
redis.call('incrby', stockKey, -1)
-- 3.4.记录用户（sadd 进集合，一人一单的判断依据）
redis.call('sadd', orderKey, userId)
return 0                          -- 0 = 资格通过
```

### 3.2 五个易错点（前四个今天全部真实踩过！）

| # | 坑 | 后果 | 教训 |
|---|---|---|---|
| 1 | `local stockKey = ...` 写了两遍，第二个本该叫 `orderKey` | 后面引用 `orderKey` 是 **nil**，sismember 对 nil 操作直接脚本报错 | Lua 是脚本，**没有编译器帮你查变量名**，变量重名就是静默覆盖 |
| 2 | key 少了冒号：`'seckill:stock'..id` 拼出 `seckill:stock10` | 和预热的 `seckill:stock:10` 对不上，`get` 返回 **nil** → `tonumber(nil)` 报错 | key 格式两边必须逐字符一致 |
| 3 | `sisimember` 拼写错误 | Redis 返回 unknown command → 脚本抛异常 | 命令名拼错没有提示，EVAL 一下就现形 |
| 4 | 结尾漏写 `return 0` | 资格通过时返回 nil → Java 侧 `result.intValue()` **NPE** | Lua 函数没有隐式返回值，"走到最后"≠"返回 0" |
| 5 | `if (sismember...)` 裸判断（不写 `== 1`） | **Lua 里只有 nil 和 false 是假，数字 0 也是真！** sismember 返回 0 会误判为"买过" | 和 C/Java 完全相反的语言习惯，条件必须显式比较 |

> **温馨小贴士：写 Lua 脚本的正确姿势**——写完先在 redis-cli 里手测，再接进 Java：
> ```bash
> redis-cli -a 123321 eval "return redis.call('get','seckill:stock:10')" 0
> ```
> 能在命令行里看到预期返回值，再放进项目跑。今天的四个坑全部能在这一步暴露，不用启动应用挨个撞。

### 3.3 Java 调用 + 返回值映射（ch6.2 后半）

```java
private static final DefaultRedisScript<Long> SECKILL_SCRIPT;
static {
    SECKILL_SCRIPT = new DefaultRedisScript<>();
    SECKILL_SCRIPT.setLocation(new ClassPathResource("seckill.lua"));
    SECKILL_SCRIPT.setResultType(Long.class);
}

Long result = stringRedisTemplate.execute(
        SECKILL_SCRIPT,
        Collections.emptyList(),                    // KEYS 为空
        voucherId.toString(), userId.toString()     // 全走 ARGV
);
int r = result.intValue();
if (r != 0) {
    return Result.fail(r == 1 ? "库存不足" : "不能重复下单");
}
```

> **小贴士**：这里 KEYS 空着、key 在脚本内拼接——**能跑**（单机 Redis），但不符合 Redis Cluster 规范（脚本要求访问的 key 落在同一 slot，key 必须外置传 KEYS 才能路由）。课程为省事这么写，知道局限即可，04 篇 unlock.lua 就是规范的 KEYS/ARGV 写法。
> **返回值语义**：0/1/2 三个数字是脚本和 Java 之间的"暗号"——返回 Long，`intValue()` 转 int 做分支，**别忘了 Lua 缺 return 会返回 null 导致这里 NPE**（坑 #4 的下游后果）。

## 四、阻塞队列异步下单（ch6.3 ★ 第二个核心）

### 4.1 生产者-消费者模型（对着代码认角色）

```
请求线程（生产者）：资格通过 → 造订单对象 → orderTasks.add(订单) → 返回订单号
                                        ↓
              ArrayBlockingQueue（出餐口：有界的内存队列，FIFO）
                                        ↓
后台单线程（消费者，@PostConstruct 启动）：orderTasks.take() 取单 → Redisson锁 → 事务写库
```

- `ArrayBlockingQueue`：**有界**（本项目 `1024*1024`）数组队列。为什么有界：内存有限，无界队列高峰期会一直吃内存直到 OOM——宁可满了拒绝（`add` 抛异常）。
- `take()` vs `poll()`：**take() 队列为空时阻塞等待**（消费者歇着等下一单，不空转烧 CPU）；poll() 立刻返回 null。
- `Executors.newSingleThreadExecutor()`：**为什么单线程**？① 写库是行锁串行，多线程并行写没有收益还互相堵；② 单线程天然保证订单按序落库，一人一单的 count 兜底更稳。
- `@PostConstruct init()`：容器启动时就提交消费者任务——不是等第一个请求来了才启动（否则第一单之前队列没人在消费）。

### 4.2 两个"异步线程专属"的坑（★ 课程重点 + 今天真实踩过）

**坑一：ThreadLocal 断了——UserHolder.getUser() 是 null**

`UserHolder` 基于 ThreadLocal，值是登录拦截器在**HTTP 请求线程**里塞的。异步后台线程是全新的线程，ThreadLocal 里什么都没有 → `getUser()` 返回 null → NPE。
**解法**：userId 在请求线程里就取好，**塞进订单对象带过去**——消费者只从 `voucherOrder.getUserId()` 拿，绝不碰 UserHolder。

**坑二：代理拿不到——AopContext.currentProxy() 在后台线程炸**

`currentProxy()` 底层也是 ThreadLocal，只在"代理方法的调用栈内"有效（03 篇 exposeProxy 那套）。后台线程里调用它直接 IllegalStateException。而 `createVoucherOrder` 要开事务（`@Transactional`），必须**通过代理调用**（this 调用事务静默失效，03 篇优化四）。
**解法**：请求线程里把代理拿到、存进**成员变量** `proxy`，后台线程用成员变量。

```java
// seckillVoucher（请求线程）里：
proxy = (IVoucherOrderService) AopContext.currentProxy();   // 现在能拿到，存成员变量
orderTasks.add(voucherOrder);
```

> **小瑕疵说明（面试加分）**：成员变量没有 volatile，理论上后台线程可能读到旧值。为什么恰好没炸：① 赋值发生在 `add` **之前**（消费者拿到单时 proxy 必然已赋值——顺序反了就会有 NPE 竞态）；② 单消费者线程。严谨做法是 `@Lazy @Resource` 注入自身代理。课程按简单方案讲，知道瑕疵在哪就是加分。

### 4.3 消费者与事务写库（完整代码块讲解）

```java
private void handleVoucherOrder(VoucherOrder voucherOrder) {
    //⚠️ 坑一：没有请求上下文，userId 只能从订单对象取
    Long userId = voucherOrder.getUserId();
    RLock lock = redissonClient.getLock("lock:order:" + userId);
    boolean isLock = lock.tryLock();                  // 无参：不重试 + watchdog（05篇）
    if (!isLock) { log.error("不允许重复下单"); return; }
    try {
        proxy.createVoucherOrder(voucherOrder);       // 坑二：用成员变量里的代理进事务
    } finally {
        lock.unlock();
    }
}

@Transactional
public void createVoucherOrder(VoucherOrder voucherOrder) {
    Long userId = voucherOrder.getUserId();           // 还是不能用 UserHolder！
    Long voucherId = voucherOrder.getVoucherId();
    //5.一人一单（数据库兜底校验——Redis 只是预判断，DB 才是最终真相）
    long count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();
    if (count > 0) { log.error("该用户已经购买过一次！"); return; }
    //6.扣减库存（乐观锁，真扣）
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherId).gt("stock", 0)
            .update();
    if (!success) { log.error("库存不足！"); return; }
    //7.保存订单（对象在请求线程里造好了、id 已生成，直接 save）
    save(voucherOrder);
}
```

**为什么消费者里还做 count + update**（"Redis 不是判断过了吗"）：Redis 资格判断是**预检**（快，挡掉 99% 无效流量），数据库校验是**兜底**（两份数据可能不一致）。判断通过到真正写库之间隔着队列排队的时间，兜底必须保留。注意返回值从 `Result` 改成 **void**——调用方是后台线程，结果无人接收，失败只能 log。

### 4.4 全流程时序（手画题）

```
用户请求 ──→ seckillVoucher（Tomcat线程，全程无DB访问！）
              ① Lua判断资格（0/1/2）         ←—— 唯一的"慢"操作？不，纯内存微秒级
```

## 六、阻塞队列版的三宗罪 → 消息队列动机（ch7 钩子）

| # | 问题 | 具体场景 | 严重性 |
|---|---|---|---|
| 1 | **内存有界** | 队列 `1024*1024` 也就百万级；真·爆款秒杀 10 万 QPS 涌入，`add` 满了直接抛异常 → 丢单 | 高 |
| 2 | **不可持久化** | 订单在 JVM 内存里，**服务重启/宕机 → 队列清空**。用户明明拿到"下单成功"的订单号，订单却永远没写库——最恶劣的故障 | 极高 |
| 3 | **不能跨 JVM** | 集群部署时两台 Tomcat **各有各的队列**，消费者不共享，容量和可靠性都不叠加 | 中 |

**消息队列（ch7）逐条对症**：消息存在 Redis/MQ 服务器上（脱离 JVM → 解决 1、2）；生产者消费者跨进程跨机器共享一个队列（解决 3）。课程路线：**7.2 List 版（LPUSH+BRPOP）→ 7.3 PubSub 版（广播，不持久化）→ 7.4/7.5 Stream 版（持久化+消费者组，最接近专业MQ）→ 7.6 用 Stream 改造本篇秒杀**。学的时候拿这三宗罪当评分表，给每个方案打分。

## 七、★ 本模块踩坑记录（2026-11-22 全部真实踩过，Claude 检查补齐）

| # | 坑 | 现象 | 修复 |
|---|---|---|---|
| 1 | Lua 变量重名（两个 stockKey） | orderKey 是 nil，sismember 报错 | 变量名检查，脚本写完先 EVAL 手测 |

## 八、八股结合点

1. **生产者-消费者模式**：阻塞队列是标准载体；对比 `wait/notify` 手搓版；`ArrayBlockingQueue`（数组+一把锁）/`LinkedBlockingQueue`（链表+两把锁，吞吐高）/`SynchronousQueue`（零容量直接交接）。
2. **线程池**：`newSingleThreadExecutor` 为什么不推荐 `Executors` 直接建（阿里规约：手动 `new ThreadPoolExecutor` 明确参数防队列无界 OOM）——本项目跟课程走，规约知道即可。
3. **ThreadLocal 与异步**：ThreadLocal 随线程走，**换线程必丢**；跨线程传数据的正路：参数传递（本项目）/`InheritableThreadLocal`（有限场景）/`TransmittableThreadLocal`（线程池场景，了解）。
4. **Spring 事务与代理**（03 篇优化四的复用）：后台线程里 `currentProxy()` 拿不到的原因（ThreadLocal 绑定调用栈）；替代方案 `@Lazy` 注入自身代理。
5. **Redis 预扣库存**：业界标准玩法（电商秒杀通用），关键词"预扣+异步落库+DB兜底"；局限（两份数据一致性/补偿）主动说 = 加分。
6. **接口签名一致性**：改实现必须同步改接口（编译器强制"不是抽象类但未覆盖抽象方法"）——工程基本功。

## 九、面试题库

### 🔥 必背五题

1. **秒杀为什么要异步化？怎么做的？** 同步版全流程占着 Tomcat 线程几十~几百ms，线程池有限、写库行锁串行是终瓶颈。异步化：请求线程只用 Lua 在 Redis 里判断资格（库存+一人一单+预扣，微秒级），通过则订单进阻塞队列、**立即返回订单号**；后台单线程慢慢写库。耗时降到 1/1000，吞吐数量级提升。
2. **Lua 脚本具体做了什么？为什么必须用 Lua？** 判库存（get+tonumber）、判一人一单（sismember）、预扣库存（incrby）、记录用户（sadd），返回 0/1/2。四步是组合操作，多条命令不原子（04 篇结论），Lua 整段作为一条命令独占执行；MULTI 写不了分支逻辑。
3. **下单请求返回后订单还没写库，用户拿订单号查不到怎么办？** 诚实版答案：阻塞队列版确实有这个窗口（排队+消费延迟，通常毫秒级）；前端拿订单号后轮询/订单列表最终可见。根本问题在内存队列不可靠 → 换 Stream/MQ（持久化+消费者组）。
4. **异步线程里有什么坑？** 两个专属坑：① ThreadLocal 断——UserHolder 拿不到用户（NPE），userId 塞进订单对象带过去；② 代理断——`AopContext.currentProxy()` 在后台线程拿不到（它也基于 ThreadLocal），请求线程里取好存成员变量（或 `@Lazy` 注入自身代理），否则 `@Transactional` 静默失效。
5. **阻塞队列版有什么问题？怎么解决？** 三宗罪：内存有界（满了丢单）、不可持久化（宕机全丢，用户已收到成功响应）、不能跨 JVM（集群队列不共享）→ Redis Stream 消息队列：消息持久化在 Redis、消费者组跨进程消费（ch7.6 改造）。

### ⚡ 追问链

- 资格判断 →"Redis 和 DB 库存不一致怎么办？"（消费者 count+update 兜底；真实生产要补偿/对账——主动说局限）
- 预热 →"库存怎么进 Redis 的？"（上线/活动前预热灌入；大促还会做库存分桶防热点 key——延伸词）
- 单线程消费者 →"消费太慢队列堆爆怎么办？"（有界 add 拒绝是设计行为；Stream 有长度上限+消费者组水平扩容）
- watchdog →"消费者锁为什么用无参 tryLock？"（不重试语义正确：重复单立即拒；watchdog 防写库慢于 30s 丢锁）
- 时序 →"proxy 赋值为什么在 add 之前？"（消费者拿到单可能立刻执行，晚了 NPE——竞态意识）
